# Human Test Checklist: FreighterData metadata row, and splitting "we wrote" from "the source changed"

**Target version:** v0.6.4 — **provisional.** This work is not released. The version is chosen by the maintainer at the last-mile gate and this filename may need renaming.
**Ships with commit:** TBD — uncommitted at the time of writing
**Companion automated tests:** 554 passing overall (was 546). The eight new tests live in `tests/test_journal.py` (48 total), `tests/test_cargo_contract.py` (25 total) and `tests/test_daemon.py` (38 total). `flake8 --select=E9,F63,F7,F82` reports 0.

## What this is

Three units of work that make the fleet carrier tab say how far it can be trusted. They change what gets written to a real Google Sheet, and **no automated test has ever written the new row to one** — every grid test builds a list in memory and asserts against it. This document is the part a person has to run.

It is written to be runnable by anyone with a Frontier account and a spreadsheet, not only by the maintainer. Sections 4 and 5 need the game running and a real 14–31 minute wait; they are marked **MANUAL** and cannot be faked.

## What shipped

**U0 — a carrier jump no longer reports you adrift** (`APITool/journal.py`). `CarrierJump` used to sit with `FSDJump` and unconditionally cleared the docking state. Measured across the real 682-file journal: **six of seven `CarrierJump` events carry `Docked: true` with `StationType: FleetCarrier`** — the commander is standing on the carrier as it moves. `Location` and `CarrierJump` are now both read as *reporting* a docking state rather than changing one.

**U1 — `FreighterData` gained a metadata row** (`APITool/google/exporter.py`), closing #19. Row 1 was an empty spacer — this was the only generated tab that could not say when it was written. It now carries `Last checked` and `Last changed`, labels in columns B and D, values in C and E, matching `ShipCargo`'s idiom. **Nothing moves:** header still row 2, TOTAL still row 3, commodities still from row 4.

**U2 — the loop stopped reading "we wrote" as "the source caught up"** (`APITool/daemon.py`). `PublishResult` gained `changed`; the tick loop keys the confirmation retry on it. The carrier publisher now writes on *every* successful check, so `Last checked` means what it says.

### Why the stamps are named the way they are

`MarketData` and `ShipCargo` head their grids with `Updated (UTC)` — the *game's* own event timestamp, because those tabs read files the game wrote.

This tab cannot do that. A live fleet-carrier payload was captured on 2026-09-15 and searched: **there is no as-of timestamp anywhere** — none at the top level, and none on a cargo item (`commodity`, `locName`, `mission`, `originSystem`, `qty`, `stolen`, `value`). Frontier's endpoint also lags the game by 14–31 minutes, so the moment of the fetch is emphatically not the moment the data describes.

So both stamps here are **our clock** and say so. An `Updated (UTC)` column on this tab, matching the others, would be a claim about the data's age that nothing in the payload supports. **If you see `Updated (UTC)` on `FreighterData` during this run, that is a failure, not a cosmetic difference.**

## Prerequisites

1. **A Frontier account with a fleet carrier**, authenticated: `edapitool auth`
2. **A configured spreadsheet id** — `--sheet-id`, `ED_SHEET_ID`, or `sheet_id` in `~/.ed_capi_config.json`
3. **Elite Dangerous running** for Sections 4, 5 and 6 only. Sections 1–3 work from a cold start
4. **Stop any `serve` you already have running.** A second one publishes to the same tab and the two will interleave, which makes every observation in Sections 4 and 5 unreadable. Ctrl-C the existing one first and restart it when you are done

### Safety

- **Every test here targets `FreighterData` and nothing else.** The tool generates that tab in full and rewrites it wholesale. The write allowlist refuses any other tab for this export — but do not go looking for the edge: a tab holding hand-entered work is not recoverable if something goes wrong
- **Note your "before" values first** (step 0 below). Several checks are before/after comparisons and there is no way to recover the "before" once the tab is rewritten

### Reset between sections

`edapitool carrier --export google` rewrites `FreighterData` wholesale, so **re-running it is the reset.** Nothing else needs undoing and no file on disk is modified by these tests.

### HV.1 — The metadata row appears and nothing moved

Validates: U1's whole claim, and the layout property that protects several hundred formulas.

- [ ] **Steps:**
  1. `edapitool carrier --export google`
  2. Open `FreighterData` in the browser
- [ ] **Expected:**
  - **B1** reads `Last checked`, **C1** an ISO timestamp of a few seconds ago
  - **D1** reads `Last changed`, **E1** either a timestamp or **empty**
  - **B2** still `Commodity` — the header did **not** move
  - **B3** still `TOTAL`
  - **B4** still holds a commodity, same as your step 0 note
- [ ] **Why this matters:** if the header moved off row 2 or commodities off row 4, every formula in the workbook addressing this tab by row is now pointing at the wrong thing — silently.

### HV.2 — The stamps are ours, not Frontier's

Validates: the measured fact that Frontier supplies no as-of time.

- [ ] **Steps:** read the labels in **B1** and **D1**
- [ ] **Expected:** exactly `Last checked` and `Last changed`. **`Updated (UTC)` must NOT appear on this tab.**
- [ ] **Why this matters:** `Updated (UTC)` would tell a reader the figure is as fresh as the timestamp. It is not — it is 14–31 minutes older than the moment we asked, and Frontier gives us no way to know by how much.

### HV.3 — The lookups still work

Validates: that adding a row did not disturb the `$B:$D` contract the workbook depends on.

- [ ] **Steps:** go to the settlement tab and row you noted in step 0
- [ ] **Expected:** the **"In Carrier Now"** value is **identical** to what you wrote down. No `#N/A`, no `#REF!`, no blank, no different number.
- [ ] **Why this matters:** this is the single most expensive way this change could fail. A shifted lookup index returns a plausible-looking wrong number rather than an error.

### HV.4 — The totals still total

Validates: the generated `=SUM()` ranges did not absorb the metadata row.

- [ ] **Steps:** click **C3**, then **E3**, and read the **formula bar**
- [ ] **Expected:** both are `=SUM(...)` starting at **row 4** — e.g. `=SUM(C4:C68)`. Neither starts at row 1, 2 or 3. The displayed totals match your step 0 note (unless the hold genuinely changed).
- [ ] **Why this matters:** a total that includes its own row, or the metadata row, is wrong in a way that looks like a plausible number.

### HV.5 — An unknown "last changed" is blank, not invented

Validates: the deliberate choice that we never guess a timestamp.

- [ ] **Steps:** after a *fresh* `edapitool carrier --export google` on a process that has not run before, read **E1**
- [ ] **Expected:** **empty.** A one-shot `carrier` command has no memory of a previous reading, so it has nothing to say about when the hold last changed.
- [ ] **Why this matters:** an invented "changed just now" is a claim, and the more dangerous one for looking reassuring.

### HV.6 — Re-running is idempotent

Validates: the write path is stable and the reset procedure actually resets.

- [ ] **Steps:** run `edapitool carrier --export google` twice in a row
- [ ] **Expected:** **C1** advances to the new time both runs; everything else is unchanged; no duplicated rows, no blank row creeping in above the header.
- [ ] **Why this matters:** this is the reset step for every section below. If it is not clean, nothing after it is trustworthy.

## Section 1: The grid, read cell by cell (~5 min, no game needed)

### 1.1 Row 1 holds labels in the key column

- [ ] **Steps:** click **B1**, **C1**, **D1**, **E1** in turn and read the **formula bar** each time, not the rendered cell
- [ ] **Expected:**
  - `B1` = `Last checked` (literal text, not a formula)
  - `C1` = an ISO-8601 timestamp to the second, e.g. `2026-09-15T22:17:18+00:00`
  - `D1` = `Last changed`
  - `E1` = an ISO timestamp or empty
  - **A1** = empty (the margin column, unchanged)
- [ ] **Check:** the labels are in **B** and **D**, the values in **C** and **E** — not the other way round. Labels sit in the key column deliberately: a `VLOOKUP` over `$B:$D` can then never land on a metadata row, because no commodity is named "Last checked".

### 1.2 The timestamp is UTC and recent

- [ ] **Steps:** compare `C1` against the current UTC time
- [ ] **Expected:** within a minute of when you ran the command. It carries an explicit offset (`+00:00`), so there is no ambiguity about which clock it is on.
- [x] **SETTLED 2026-09-15 by API readback — the stamp stays TEXT.**

  `FreighterData` is the **only** generated tab written with `value_input_option="USER_ENTERED"` (`exporter.py:555`); `MarketData` and `ShipCargo` both go through `RAW`. `USER_ENTERED` is required here — row 3's `=SUM()` and column E's `=C4*D4` must arrive as live formulas — but it also means Sheets parses everything else in the same payload. The open question was whether it would parse the ISO timestamp into a date serial, losing the `+00:00` offset.

  It does not. Read back three ways, `C1` is byte-identical to what was sent:

  ```
  sent              : '2026-09-15T22:55:59+00:00'
  C1 as FORMULA     : '2026-09-15T22:55:59+00:00'
  C1 as UNFORMATTED : '2026-09-15T22:55:59+00:00'
  ```

  The offset defeats Sheets' date parsing, so the value is stored verbatim. **This is the safer outcome** — the UTC anchor survives in the cell rather than becoming a naive serial in the spreadsheet's timezone, which is the shape of the bug that made a market-age formula under-report by 16.03h against a true ~20h.

  **Consequence for anyone writing a staleness formula:** `C1` is a string, so `=NOW()-C1` will not work. It has to be parsed (`DATEVALUE`/`TIMEVALUE`), and `NOW()` is spreadsheet-local while this stamp is UTC — so the offset is yours to apply. That is sheet work, deliberately: the tool publishes the fact with its offset intact and does not decide how a workbook wants to display age.

  Reproduce with `python tests/one-offs/thinking/carrier-overlay/probe_live_metadata_row.py`.

### 1.3 The column contract is intact

- [ ] **Steps:** read row 2 across: **A2**, **B2**, **C2**, **D2**, **E2**
- [ ] **Expected:** empty, `Commodity`, `Quantity`, `Unit Price`, `Total Value` — in exactly those positions
- [ ] **Check:** nothing was inserted left of **D**. Inserting a column there reindexes every `VLOOKUP` in the workbook without raising anything anywhere, which is why the automated suite guards it and why it is worth one glance here too.

### 1.4 Commodity rows carry their own Total Value formula

- [ ] **Steps:** click **E4** and read the formula bar
- [ ] **Expected:** `=C4*D4` — a formula, not a computed number
- [ ] **Check:** the row number inside the formula matches the row it is on. Spot-check one row near the bottom of the tab as well.

## Section 4: **MANUAL** — the confirmation retry against a real lag (~35 min, game required)

This is U2's entire reason for existing and it **cannot be automated**. It needs a real cargo transfer and a real wait for Frontier to catch up.

### 4.1 Watch a transfer settle

- [ ] **Prerequisites:** game running, docked at your own fleet carrier, `serve` running in a terminal you can watch, and cargo to move.
- [ ] **Steps:**
  1. Note the current `FreighterData!C1` and `E1`
  2. Transfer a **clearly identifiable** amount to or from the carrier — a few hundred tonnes of one commodity is ideal, because you want to be able to spot it
  3. Note the wall-clock time of the transfer
  4. Watch `serve`'s console for the next 35 minutes
- [ ] **Expected, in this order:**
  - Within a minute or two: `FreighterData unchanged -- stamp refreshed`
  - **That line repeats roughly once a minute**, and `C1` in the sheet advances each time
  - Somewhere between **14 and 31 minutes** after the transfer: a single `FreighterData <- N t on <callsign>`, the quantities change, and **E1** (`Last changed`) jumps to that moment
- [ ] **The failures to watch for:**
  - **It stops refreshing after the first one.** That is the confirmation split failing — the loop read a write as "done" and retired the retry. This is the exact bug U2 exists to prevent
  - **It never writes the real change**, and the number only corrects itself much later on the heartbeat. Same failure, different symptom
  - **It writes the change immediately.** That would mean Frontier stopped lagging, which would be genuinely interesting — note it, because several design decisions rest on that lag
- [ ] **Record:** the gap between your transfer and the `FreighterData <- ...` line. That number is the measured lag for this session, and it is worth keeping — the whole design rests on one prior measurement of it.

### 4.2 The distinction the two stamps exist to make

- [ ] **Steps:** during the waiting period in 4.1, look at `C1` and `E1` together
- [ ] **Expected:** `C1` is seconds old (we are checking constantly), `E1` is minutes or hours old (the hold has not moved since then)
- [ ] **Why this matters:** "we have not looked" and "we looked and nothing has changed" were indistinguishable before this work. That is how this tab sat 5,348 t stale with nothing on the sheet to show it.

## Section 5: **MANUAL** — `Last changed` after a restart (~5 min, game helpful)

### 5.1 An unknown stamp goes blank rather than lying

- [ ] **Steps:**
  1. With `serve` running and `E1` showing a real timestamp, **Ctrl-C** it
  2. Start `serve` again
  3. Wait for the first carrier publish (up to a minute with events, up to 15 on a quiet session)
  4. Read `E1`
- [ ] **Expected:** **`E1` is empty.**
- [ ] **Why this is right, and not a bug:** `Last changed` is held in the process only. After a restart the honest answer is "not known". Defaulting it to the current time would assert the hold had just changed — a claim, and the more dangerous one for looking reassuring. An empty cell is a fact your own formulas can branch on.
- [ ] **Check:** `C1` (`Last checked`) is **not** blank — it is current. Only the changed-stamp is forgotten.

### 6.1 Jumping while aboard does not make the tool lose you

  3. After arrival, check `MarketData`'s station/system header block and `serve`'s console output

### 6.2 A jump you were not aboard for still undocks you

- [ ] **Expected:** docking state stays as it was for your actual location

### 7.1 No quota errors during an active session

- [ ] **Steps:** during the busiest part of a cargo session with `serve` running, watch the console
- [ ] **Expected:** no `429`, no `RESOURCE_EXHAUSTED`, no `Quota exceeded`

## What the automated tests DON'T cover

The reason this document exists.

- **Any write to a real Google Sheet.** Every grid test builds a list in memory. The first real `gspread` write of the metadata row happens when a human runs Section 1. A value-write and a correct-write render identically — which is exactly how a defect in column L stayed invisible for three releases. **Read the formula bar, not the cell.**
- **The workbook's own formulas.** Several hundred `VLOOKUP`s point at `FreighterData!$B:$D`. The suite asserts indices against an in-memory grid; only the live sheet proves nothing broke.
- **Frontier's real lag.** Every daemon test uses a fake clock and a fake source. Whether the retry actually settles a real transfer at real speed is Section 4 and nothing else.
- **Process restart.** `Last changed` living in memory is a design decision that can only be observed by killing and restarting the process.
- **A real carrier jump**, which needs the game, a cooldown and travel time.
- **Google's write quota** under a real session's traffic.
- **How Sheets renders an ISO timestamp** in the reader's locale and column width.
- **Whether the two stamps are actually legible** side by side to someone who did not write them. If `Last checked` and `Last changed` are confusing in practice, that is worth reporting — it is a design problem no assertion can catch.
