# Human Test Checklist: a region can hold any data

**Target version:** 0.8.2 (the version is the maintainer's to choose at commit)
**Ships with commit:** TBD, uncommitted over `ca00b11` (v0.8.1)
**Companion automated tests:** 21 in `tests/test_region_binder.py`; 9 in `tests/test_config_regions.py` updated to the three-field binding. Suite: 1,073.

## What this is

A `bindings` entry in the `regions` plugin's config (the `construction` plugin and its `construction_regions` key until this version) can now name its data: `"data": "market"`, `"cargo"` or `"carrier"`, with `construction` as the default. `serve` keeps such a region current with the grid the `MarketData`, `ShipCargo` or `FreighterData` tab holds. The automated tests drive the real daemon with a fake Google exporter, so they prove the right grid reaches the writer, never that it lands correctly in a real sheet. This checklist covers the real sheet. About 10 minutes.

## Prerequisites

1. EDAPITool installed from this tree, and Google Sheets access that already works (`edapitool market --update-sheet --dry-run` succeeds).
2. **Your own copy** of the template workbook. In it, right-click any tab you keep by hand, choose **Duplicate**, and call the copy `RegionTest`. Every write below goes to `RegionTest`.
3. A scratch config directory, so your real config and store are untouched. `ED_CONFIG_DIR` moves the config, the store, **and** where the Google credentials are read from, so copy the two credential files in. Copy them only; do not open or print them.

   **cmd.exe**:
   ```cmd
   mkdir %TEMP%\edregion
   copy "%USERPROFILE%\edapitool\gsheet_credentials.json" %TEMP%\edregion\
   copy "%USERPROFILE%\edapitool\gsheet_token.json" %TEMP%\edregion\
   set ED_CONFIG_DIR=%TEMP%\edregion
   ```

   **PowerShell**:
   ```powershell
   New-Item -ItemType Directory -Force "$env:TEMP\edregion" | Out-Null
   Copy-Item "$env:USERPROFILE\edapitool\gsheet_credentials.json", "$env:USERPROFILE\edapitool\gsheet_token.json" "$env:TEMP\edregion\"
   $env:ED_CONFIG_DIR = "$env:TEMP\edregion"
   ```

   **POSIX**:
   ```bash
   mkdir -p /tmp/edregion
   cp ~/edapitool/gsheet_credentials.json ~/edapitool/gsheet_token.json /tmp/edregion/
   export ED_CONFIG_DIR=/tmp/edregion
   ```

4. Write `config.json` in that directory, replacing `YOUR_COPY_ID` with your copy's id. Each section below says which `regions` list to use:

   ```json
   {
     "targets": {
       "region-test": {
         "kind": "gsheet",
         "plugin": "regions",
         "id": "YOUR_COPY_ID",
         "config": {
           "bindings": [
             {"region": "RegionTest!P1:U40", "data": "cargo"}
           ]
         }
       }
     }
   }
   ```

5. Have something in your ship's hold, and be docked at a station with a market.

**Reset between sections:** edit the `regions` list, and clear `RegionTest` by selecting its cells and pressing Delete.

## High-Value Verification (~5 minutes)

### HV.1 -- A cargo region holds exactly what ShipCargo holds

Validates: the region places the same grid the tab publisher built, into the right rectangle, and nowhere else.

- [ ] **Steps:**
  1. Type `marker` into `RegionTest!O1` and `RegionTest!V1`, just outside the region.
  2. With the cargo entry from the prerequisites, run `edapitool serve --once`.
- [ ] **Expected:**
  - The output has a line `  RegionTest!P1:U40 <- N rows (ShipCargo)`.
  - `RegionTest!P1:U40` shows the same rows and values as the `ShipCargo` tab.
  - `O1` and `V1` still say `marker`.
- [ ] **Why this matters:** the whole promise is "exactly what the tab holds, only inside the region".

### HV.2 -- A market region, and a region too small for it

Validates: the market kind, and the refusal when a grid outgrows its reserve.

- [ ] **Steps:**
  1. Set the list to `[{"region": "RegionTest!H1:N200", "data": "market"}]` and run `edapitool serve --once`.
  2. Change the region to `RegionTest!H1:N10` and run it again.
- [ ] **Expected:**
  - Step 1: `RegionTest!H1:N200` matches the `MarketData` tab.
  - Step 2: a refusal naming the market's size in rows and columns and the reserve of 10 rows. Nothing below row 10 changes, and nothing outside `H:N` changes.
- [ ] **Why this matters:** a real market runs past a hundred commodities, and an undersized region must refuse, never spill.

### HV.2b -- A carrier region holds exactly what FreighterData holds

Validates: the carrier kind, placed by the carrier publisher itself with the tab's own stamps. Needs a Frontier login (`edapitool auth`).

- [ ] **Steps:**
  1. Set the list to `[{"region": "RegionTest!W1:AA300", "data": "carrier"}]` and run `edapitool serve --once`.
  2. Run it again a minute later.
- [ ] **Expected:**
  - The carrier line is followed by `  RegionTest!W1:AA300 <- N rows (FreighterData)`.
  - The region matches the `FreighterData` tab, including its `Last checked` and `Last changed` cells.
  - After step 2 the region's `Last checked` has moved, exactly as the tab's has.
- [ ] **Without a login:** in a scratch dir with no Frontier token, `edapitool serve` prints `NOT published: RegionTest!W1:AA300 -- a carrier region needs a Frontier login` when it starts.
- [ ] **Why this matters:** the carrier's hold is the data most worth placing beside a hauling plan, and its stamps are what tell you whether it is current.

### HV.3 -- A bad entry is refused when the tool starts, by name

- [ ] **Steps:**
  1. Set the list to `[{"region": "RegionTest!P1:U40", "data": "journal"}]` and run `edapitool plugins`.
  2. Set it to `[{"region": "RegionTest!P1:U40", "data": "cargo", "site": "Anywhere"}]` and run `edapitool plugins` again.
- [ ] **Expected:**
  - Step 1 names `bindings[0]` and lists the kinds that exist: `construction, market, cargo, carrier`.
  - Step 2 names `bindings[0]` and says a `"site"` only chooses a construction build.
  - `edapitool serve --once` with either entry refuses the same way and writes nothing.
- [ ] **Why this matters:** a binding silently skipped is a region that quietly stops updating.

### HV.3b -- A 0.8.1 config naming the `construction` plugin, and its two-line move

Validates: the rename is loud, not silent, and the documented fix works.

- [ ] **Steps:**
  1. In the scratch config, name the plugin `"construction"` and the key `"construction_regions"`, as 0.8.1 wrote them, and run `edapitool plugins`.
  2. Make the two edits from the CHANGELOG, `"plugin": "regions"` and `"bindings"`, and run `edapitool plugins` again.
- [ ] **Expected:**
  - Step 1: `construction` is reported as not found for that target; nothing is published for it.
  - Step 2: `regions` is loaded and serves the target, with no config problem.
- [ ] **Why this matters:** a plugin that silently stopped loading would look like a sheet that stopped updating.

### HV.4 -- An old construction entry still behaves exactly as before

- [ ] **Steps:**
  1. Set the list to `[{"region": "RegionTest!R1:AC60", "site": "<a build your journal knows>"}]`, with no `data`, and run `edapitool serve --once`.
- [ ] **Expected:** the construction block appears in `R1:AC60`, exactly as it did under 0.8.1.
- [ ] **Why this matters:** every existing binding has no `data` field.

### HV.5 -- The flag is still a construction block

- [ ] **Steps:** run `edapitool serve --once --construction-region "RegionTest!R1:AC60=<the same build>"`.
- [ ] **Expected:** the same construction block, and the config list is ignored for this run.

## Section 1: in a live session

### 1.1 The region updates in the same cycle as its tab

- [ ] **Steps:** with the cargo entry, run `edapitool serve` (no `--once`) and buy or sell one commodity in game.
- [ ] **Expected:** after the debounce, one cycle logs both the `ShipCargo` line and the `RegionTest!P1:U40` line. The region never shows a different hold from the tab.

### 1.2 Unchanged cargo is not rewritten

- [ ] **Steps:** in the same session, dock or undock without changing the hold.
- [ ] **Expected:** `RegionTest!P1:U40 unchanged (cargo) -- not written`.

A red-green audit broke twelve behaviours in turn. Fifteen of the first 20 new tests failed under at least one break; the other five are deliberate fences (a region's guard is its own rectangle, the accepted kinds, a carrier region is not a publisher of its own, and two refusals that predate this change). The 21st, added after the checklist sweep found a refused `null` quoted as Python's `None`, fails on the old message.

## What the automated tests DON'T cover

- **Real writes into a region of a real sheet:** the tests use a fake exporter and never touch Google.
- **Real market sizes against a real reserve:** the tests' markets are tiny.
- **Timing in a live session:** the same-cycle claim is proven by publisher order, not by a real journal.
- **How the refusal messages read to a person.**

## Known limits, by design

- **A carrier region publishes only with a Frontier login**, like the carrier tab. Without one, `serve` names each carrier region as not published when it starts.
- **The startup check that two targets do not write the same cells cannot see regions.** A region overlapping another plugin's declared range is not caught at load. This was already true of construction regions.
- **The `--construction-region` flag is always a construction block.**
- **The plugin keeps the name `construction`.** Binding regions is expected to move into the tool itself for every kind of data.
