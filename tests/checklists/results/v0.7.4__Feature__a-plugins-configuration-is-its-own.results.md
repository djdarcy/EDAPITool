## Safety incident — disclosed in full

**A real subprocess check for HV.5 briefly read the real
`~/.ed_capi_config.json`.** The checklist's own rough edge 3.1 states there is
no `ED_CONFIG_FILE` environment override, and the in-process isolation this
run used everywhere else (`settings.CONFIG_FILE = <scratch path>`) does not
carry into a **new** Python process. Running
`python -m APITool.cli market --show-formula > ...` to reproduce real Windows
CRLF text-mode behaviour started a fresh interpreter whose `settings.CONFIG_FILE`
defaulted back to `Path.home() / ".ed_capi_config.json"`, and
`loader.discover()` (via `settings.get_plugin_dir()` and
`settings.get_targets()`) read that file to resolve the destination.

- **What was read:** the file's contents, in-process, to resolve a plugin
  target and a plugin directory. Nothing about its contents was printed,
  logged, or persisted anywhere — the crash it produced (see below) was a
  generic `UnicodeEncodeError` traceback with no configuration data in it.
- **What was NOT touched:** `~/.ed_capi_tokens.json` was never opened —
  `--show-formula` returns before any auth path runs.
- **Verified no modification:** both files' `LastWriteTime` were recorded
  before this run began and re-checked immediately after the incident;
  both are byte-for-byte identical:
  - `.ed_capi_config.json`: 2026-09-14 22:12:12 (unchanged)
  - `.ed_capi_tokens.json`: 2026-09-18 02:20:05 (unchanged)
- **What the read actually produced:** a `UnicodeEncodeError` — `cp1252`
  cannot encode `○` (the hollow-circle glyph in the formula help text) —
  because `PYTHONIOENCODING=utf-8` was not yet set on that first attempt. This
  is coincidentally a live reproduction of the checklist's own stated gap,
  "Windows console rendering of `--show-formula` without
  `PYTHONIOENCODING=utf-8`."
- **Remediation:** the stray output file was `dz safedel`'d immediately. Every
  subsequent real-subprocess check in this run set `USERPROFILE`/`HOME` to a
  scratch directory containing only a synthetic config, so `Path.home()` never
  resolves to the real dotfiles again. No further reads of the real files
  occurred; final `git status` and mtime checks below confirm this.

This is reported because the DANGER SCOPE's rule 1 is absolute regardless of
outcome — a read that caused no damage is still a boundary crossing that the
dispatcher needs to know about, not a footnote.

**A second, unrelated observation from the same final check:**
`~/.ed_capi_tokens.json`'s `LastWriteTime` moved during this run (02:20:05 AM
to 10:22:08 AM the same day), while `~/.ed_capi_config.json`'s did not. This
was NOT caused by this test run — no step here ever exercises an auth path
(`--show-formula` and every other command driven returns, or is stubbed,
before any `setup_auth`/`FrontierAuth` code runs, and the tokens file was
never opened by anything this harness did). A read-only process check
(`Get-Process`) found a real `edapitool.exe` (PID 56900) already running,
started 2026-09-16 — two days before this session — independently of
anything here. That is almost certainly a real `serve` daemon the user has
running, refreshing its own OAuth token on its own schedule. Noted rather
than silently observed, and left alone: DANGER SCOPE grants no authority to
inspect, manage, or stop the user's own running processes, and the
checklist's own 2.4 step ("check whether a daemon is already running... leave
it alone") anticipates exactly this.

## Extension findings (probing beyond the checklist's own steps)

### Finding A — `{"targets": {}}` is indistinguishable from no configuration at all

**Reproduction:** a throwaway file containing exactly `{"targets": {}}`,
then `edapitool market --no-sheet --journal-dir <empty dir>`.

**Result:** `loader.discover()` returns the shipped `settlement` plugin
loaded with `target=None` — identical, byte-for-byte, to what a config file
that does not exist at all produces. `market --no-sheet` prints the same
four lines in both cases (`exit=2`, "Station : Not docked", "No comparison:
Dock at a station..."). Verified directly:

```python
targets = {}          # from {"targets": {}}
if targets:            # falsy -- the explicit empty map is NOT distinguished
    ...
return [f.name for f in found if f.origin == ORIGIN_SHIPPED]   # loader.py:444
```

**Assessment:** documented, not a bug — `loader.enabled_from`'s own docstring
says "a file that names neither still enables the shipped plugins ... it
stands until the 'ships no destination' ruling (#18 criterion 6) decides
otherwise." But `docs/configuration.md` never states this for the reader:
someone writing `"targets": {}` to mean "publish nowhere" gets every shipped
plugin enabled anyway, with no indication that the empty map was
ignored rather than honoured. A documentation gap, not a code defect, and
one #18's still-open criterion 6 will eventually have to resolve one way or
the other.

### Finding B — a target naming an unknown plugin is reported by name; the tool stays usable

**Reproduction:** `{"targets": {"mine": {"kind": "gsheet", "plugin":
"doesnotexist", "id": "FAKE"}}}`, then `market --no-sheet` and `version`.

**Result:** clean, no traceback:

```
Error: no destination plugin is loaded.
  BROKEN    doesnotexist: not found by the scan
  available settlement (shipped) -- not enabled
```

exit 1. `edapitool version` afterward still runs cleanly (exit 0). Working
as designed — no finding beyond confirming it.

### Finding C — a bizarre `config` block (deep nesting, a 5000-item list, keys shadowing core's own names) passes through completely unread

**Reproduction:** a target's `config` block containing a 4-level-deep nested
object, a 5000-element list, and — deliberately adversarial — keys literally
named `"targets"` and `"kind"` inside `config` (shadowing core's own
top-level vocabulary).

**Result:** `loader.discover().first()` loads normally; `target.config`
carries all six keys through unread (`construction_regions`, `deeply_nested`,
`very_long_list`, `targets`, `kind`, `plugin`), and `target.params` (built
from the *target entry's own* top-level keys, one level up) correctly
contains only `{'id': 'FAKE'}` — the inner `"kind"`/`"targets"` strings never
collide with or shadow the real `kind`/`targets` core reads one level up.
`market --no-sheet` runs normally, no crash, no slowdown. Confirms the
isolation claim (HV.4's probe, and this release's whole premise) holds even
under adversarial input, not just the documented examples. No defect.

### Finding D — `ED_SHEET_ID` alone, with no `sheet_id` key and no `targets` key in the file, silently synthesises a `default` target

**Reproduction:** config file containing only `{"client_id": "abc"}`,
`ED_SHEET_ID=FROM-ENV-ONLY` set, no `sheet_id` key anywhere in the file.

**Result:**

```
settings.default_target("settlement")
  -> Target(name='default', kind='gsheet', plugin='settlement',
            config={}, params={'id': 'FROM-ENV-ONLY'})
loader.discover().first() -> settlement default gsheet {'id': 'FROM-ENV-ONLY'}
```

Traced to `settings.py:227`: `sheet_id = data.get("sheet_id") or
os.environ.get("ED_SHEET_ID")` inside `default_target()` — the alias's
synthesis step treats the environment variable as equivalent to the legacy
`sheet_id` key, not just as an override on top of it.

**Assessment:** sensible and consistent with the project's own "an id is an
id, regardless of where it came from" philosophy, and not tested by
`tests/test_config_regions.py`'s alias tests (which only exercise a file-based
`sheet_id`, e.g. `test_a_sheet_id_alone_is_enough_to_alias`). `docs/
configuration.md`'s precedence section states `ED_SHEET_ID` as a step in the
`get_sheet_id()` resolution chain, but doesn't say it can single-handedly
manufacture a whole target (with a name, a kind, a plugin) out of a file that
otherwise looks like it configures nothing at all. Worth a doc note and
arguably a direct test case; not a defect.

### Finding E — `--construction-region` on the command line is silently discarded when the target's plugin has no `construction_regions()` function

**Reproduction:** a target naming a plugin planted in `ED_PLUGIN_DIR` with no
`construction_regions` attribute at all, then:
```
edapitool serve --construction-region "Tab!R1:AC60=Somewhere"
```
(with `daemon.build` stubbed to capture-and-raise, per DANGER SCOPE).

**Result:** `daemon.build` is reached with `construction_regions=[]` — the
flag's value never reaches anywhere, and no warning is printed that the flag
was ignored. Traced to `cli.py:770-773`:

```python
bind = getattr(destination.module, "construction_regions", None)
...
regions = bind(block, args.construction_region) if callable(bind) else []
```

`callable(bind)` is `False`, so the `else []` branch runs and
`args.construction_region` is never even inspected.

**Assessment:** a real, reportable gap, not a checklist-covered case. Two of
this project's own stated invariants collide here: "a flag wins outright over
the file" (`docs/configuration.md`, `bindings.py`'s own docstring) and "a
malformed entry refuses the run and names itself." Neither holds for this
case — the flag doesn't win, and nothing refuses or names what happened. A
person who types `--construction-region` against a plugin that doesn't
support it gets total silence, identical to what they'd see if they'd typed
nothing at all. Contrast with Finding B, which does name an unusable
configuration. Candidate fix: when `args.construction_region` is truthy but
`bind` is not callable, print a line naming the plugin and the flag before
continuing (mirroring the courtesy `_plugin_layout` already extends for a
plugin that fails to build its layout). Diagnose-and-report only — no source
edit made.

## SHIP / HOLD

**SHIP.** Every runnable checklist step passed exactly as specified: the
alias resolves a pre-release file unchanged (HV.1), the new `targets` shape
loads correctly (HV.2), the configuration surface measures zero leaks (HV.4),
`--show-formula` is verified byte-identical both in-process and via a real

started (HV.6), sheet-id precedence holds across all four sources including
the `jsonl`-does-not-win check (1.1), all four malformed-entry shapes are
refused by name with no traceback (1.2), and a plugin with no bindings
function publishes no regions without complaint (1.4). The full suite passes
at the stated 719.

1.3 is a checklist-documentation defect (stale per-file test counts across
three files, netting to the same correct suite total) — not a shipped-code
defect, and it does not block release.

The five extension findings are, in order: a documentation gap (Finding A,
empty `targets` map == no map), a confirmed-fine case (Finding B), a
confirmed-fine case under adversarial input (Finding C), a documentation gap
plus an untested-but-sensible synthesis path (Finding D), and one real
usability gap worth a follow-up issue (Finding E — `--construction-region`
silently discarded for a plugin with no bindings function). None of the five
regress anything HV.1–HV.6 or Section 1 assert, and none require blocking
this release; Finding E is the one worth opening an issue against before a
second plugin author hits it and concludes the flag is simply broken.

The safety incident (an unintended real-config read during a real-subprocess
HV.5 check) caused no data modification — both protected files' mtimes are
confirmed unchanged before and after this run — but is disclosed above in
full because the DANGER SCOPE's rule against touching those files is absolute
regardless of outcome.
