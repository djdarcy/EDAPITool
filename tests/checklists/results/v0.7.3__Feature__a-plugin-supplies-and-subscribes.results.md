### Checklist defect — 1.3's pytest command can't select the test it names

The checklist says: *"the two source-grep tests pass: neither `cli.py` nor
`service.py` contains `plugins.settlement`"*, and gives this command:

```
python -m pytest tests/test_plugin_loader.py -q -k "names_no_plugin or imports_no_plugin"
```

That command only targets `tests/test_plugin_loader.py`. The `cli.py`
source-grep test (`test_the_composition_root_names_no_plugin_and_carries_no_glyph`)
does live there and matches `names_no_plugin`, so it runs — 1 selected, 61
deselected. But the `service.py` source-grep test is
`test_the_service_imports_no_plugin`, and it lives in
`tests/test_supplier_registry.py`, not `test_plugin_loader.py` — so
`-k "... or imports_no_plugin"` deselects it silently (0 matches for that
term in the targeted file) rather than failing loudly. A checklist runner
following the command as written gets "1 passed" and a false sense that both
source-grep guarantees were checked, when only the `cli.py` one was.

Confirmed both real assertions independently hold:

```
python -m pytest tests/test_plugin_loader.py -q -k "names_no_plugin or imports_no_plugin"
  -> 1 passed, 61 deselected  (only the cli.py check)
python -m pytest tests/test_supplier_registry.py -q -k "imports_no_plugin"
  -> 1 passed, 17 deselected  (the service.py check, run directly)
```

Not a code defect — both guarantees the checklist cares about are real and
enforced. It's a copy/paste-shaped error in the checklist's own command line
(likely `service.py`'s check was added to `test_supplier_registry.py` during
the slice-B move and the checklist's step 1.3 command wasn't updated to
match). Fix is a one-line edit to the checklist's command, e.g. adding
`tests/test_supplier_registry.py` to the invocation or its own `-k` line —
diagnose-and-report only, no checklist edit made per the dispatch's "do not
edit source or tests" instruction.

## Extension findings (not checklist steps — probing beyond it, per dispatch instructions)

### Finding A — a plugin's `supplies()` colliding with core's own supplier name crashes with a raw traceback, not a clean error

**Reproduction:**

```python
# targets = {"mine": {"kind": "gsheet", "plugin": "collider"}}
# collider/__init__.py:
KIND = "gsheet"
class _Layout:
    totals_tab = "Collider Tab"
    def writes(self):
        return {}
def layout(**overrides):
    return _Layout()
def writes():
    return _Layout().writes()
def supplies():
    return {"location": lambda ctx: None}
```

```
edapitool market --no-sheet --journal-dir <empty temp dir>
```

Result: an unhandled `ValueError`, full Python traceback, no `Error: ...`
line, process exits via an unhandled exception:

```
Traceback (most recent call last):
  ...
  File "APITool\cli.py", line 339, in cmd_market
    service = MarketRefreshService(
  File "APITool\service.py", line 176, in __init__
    self.suppliers = merge_suppliers(offered)
  File "APITool\registry.py", line 132, in merge_suppliers
    raise ValueError(
ValueError: supplier 'location' is offered by both 'core' and
'edapitool_user_plugins.collider'; a supplier has one source
```

**Cause:** `cli.py`'s `cmd_market` wraps only `service.refresh(...)` in
`try/except Exception` (lines ~394-412); the `MarketRefreshService(...)`
constructor two lines above it, which is where `merge_suppliers` runs and
raises, is unguarded. `merge_suppliers`'s `ValueError` is a plugin-authoring
mistake exactly analogous to two plugins declaring overlapping sheet
writes — and that overlap case (`build_enforcer`/`declares()` in `loader.py`)
*is* caught and reported as a clean, named `Error: ...` line at load time.
The supplier-name collision is the newer half of the same contract
(`registry.py`'s own docstring calls it "the supplier-side twin of two
plugins declaring the same cells") and was not given the same treatment.

Not filed as a FAIL against a checklist step (no HV/1.x/2.x step exercises a
colliding `supplies()`), reported as a finding per the dispatch instructions.
Candidate fix: either wrap the `MarketRefreshService(...)` construction in
`cmd_market` in the same `except Exception as exc: print(f"Error: {exc}")`
the refresh call already has, or validate `merge_suppliers` at plugin
load/discovery time (alongside the existing `writes()` overlap check) so the
failure is reported by the loader before any command tries to construct a
service. Diagnose-and-report only — no source edit was made.

### Finding B — a plugin's `subscribes()` naming an unknown supplier never runs, and never errors, under `--no-sheet`

**Reproduction:**

```python
# targets = {"mine": {"kind": "gsheet", "plugin": "ghostplug"}}
# ghostplug/__init__.py:
KIND = "gsheet"
class _Layout:
    totals_tab = "Ghost Tab"
    def writes(self):
        return {}
def layout(**overrides):
    return _Layout()
def writes():
    return _Layout().writes()
def subscribes():
    from APITool.registry import Subscription
    return [Subscription("ghost", ("nonexistent_supplier",), lambda ctx: "boo")]
```

```
edapitool market --no-sheet --journal-dir <empty temp dir>
```

Result: no exception, no error line — a completely ordinary run (exit 2,
`Station   : Not docked` / `No comparison: Dock at a station to compare its
market.`, identical in shape to what the same command prints with no plugin
subscriptions at all).

**Cause:** `service.py`'s `refresh()` only reaches `_finish()` (which is the
only place `ctx.run(self.subscriptions)` is called) when a worksheet is
present — `--no-sheet` means `worksheet=None`, so `refresh()` returns before
`_finish` regardless of location/dock state. A misconfigured `subscribes()`
is therefore silently inert under `--no-sheet`; the checklist's own
"same question" framing (asking to run this through `--no-sheet`) can't
actually exercise the bad-subscription code path at all, by design of the
early-return, not by an oversight in this test.

To confirm what a real, worksheet-bearing run *would* report, the actual
push mechanism was exercised directly, in-process, with no CLI/network
involved (`APITool.registry.Refresh(...).run([...])` called on a
`Subscription` naming an unknown supplier):

```
KeyError: "no supplier named 'nonexistent_supplier'; known suppliers: other"
```

That `KeyError`, if raised inside a real `service.refresh(...)` call, *would*
be caught by `cmd_market`'s existing `except Exception as exc: print(f"Error:
{exc}")` and shown as a clean `Error: no supplier named 'nonexistent_supplier';
known suppliers: ...` line — unlike Finding A, this path already has correct
error handling; it simply never got a chance to run under this checklist's
`--no-sheet` framing. Not a defect. Recorded as a finding because the
checklist doesn't state that `--no-sheet` makes this case unreachable, and a
future checklist author asking "what does a bad subscription look like" would
need `--update-sheet` (out of DANGER SCOPE here) or a direct registry call
(as done above) to see it.
