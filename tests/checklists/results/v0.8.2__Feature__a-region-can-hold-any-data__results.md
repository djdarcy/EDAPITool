**Note on the "older shape" example:** the doc's code fence is written as illustrative `jsonc` (a leading `//` comment above the JSON), explicitly captioned "shown so you can recognise your own file" -- it is not presented as literal input. Pasted verbatim it fails to parse, because `config.json`'s own comment rule (documented a few paragraphs earlier in the same file) only tolerates `#` lines in a header, never `//` anywhere. This is correct, expected behaviour given the documented comment rule, not a defect -- but it is worth flagging that a reader who copies the fenced block character-for-character (as the checklist's own step 2 instructs: "paste each into a scratch config.json") will hit a parse warning rather than seeing the "old shape" behaviour the surrounding prose describes. The tool's response to the bad paste is itself graceful (a named warning, then "running with no settings", exit 0 -- no crash, no traceback), so nothing is *broken*; the rough edge is purely in how directly copy-pasteable that one example is.

| 2 | `"data": null` | Refused: `has "data": None; a region can hold construction, market, cargo, carrier` | Reasonable, but the message renders Python's `None` rather than JSON's `null`. Minor cosmetic rough edge, not a functional bug (same underlying `!r}` formatting a JSON string value gets, e.g. case 1 and 3 render with Python single-quotes too, so this is a pre-existing convention throughout the message, not something new to this feature). |
| 3 | `"data": ""` | Refused: `has "data": ''; a region can hold construction, market, cargo, carrier` | Yes. |
| 4 | carrier entry with `"site": ""` | **Not refused** -- loads cleanly, no CONFIG line | Consistent with the pre-existing, deliberately-pinned asymmetry documented in `test_config_regions.py::test_an_empty_site_means_the_same_as_an_absent_one` (an empty site normalises to `None` for *any* kind before the "site only chooses a construction build" check runs). Reasonable as an extension of an existing, already-accepted design decision -- but worth naming explicitly, because it means typing `"site": ""` on a carrier/market/cargo entry to "clear" a site is silently accepted rather than refused as meaningless, the same way a non-empty site there IS refused (see #5). |
| 5 | carrier entry with `"site": "   "` (whitespace, non-empty) | Refused: `names a "site", which only chooses a construction build; a carrier region shows the carrier as its tab does` | Yes -- and it confirms the refusal message correctly substitutes the actual kind name (`carrier`, not a hardcoded `cargo`) into both places in the sentence. Worth a maintainer's eye, but it is an existing, tested, and documented asymmetry (test_config_regions.py comment: "recorded as a rough edge in this version's checklist"), not a new regression. |
| 6 | a pasted flag string, `"RegionTest!R1:AC60=Badeaux Nutrition Centre"`, as a bare list entry | Loads cleanly, defaults to a construction block as documented | Yes, matches docs and `bindings.parse_entry`'s tolerated-string path. |

## Deviations from a literal reading of the dispatch

1. **`ED_PLUGIN_DIR` forced to an empty scratch guard directory for every command**, not only where the config happened to need it. One of the docs examples (`configuration.md`'s "The shape", the full two-target config) sets `"plugin_dir": "~/edapitool/plugins"` verbatim inside the pasted JSON. Per `APITool/settings.py::get_plugin_dir()`, the precedence is `ED_PLUGIN_DIR` env var, then the config file's own `"plugin_dir"` key, then `~/edapitool/plugins` -- and critically, a `"plugin_dir"` key written *inside* the config file is **not** relocated by `ED_CONFIG_DIR`; only the *default* (no key, no env var) is. Pasting that example verbatim, with only `ED_CONFIG_DIR` set, would have made `edapitool plugins` scan-list the real `~/edapitool/plugins` directory -- a direct hit on the "never read, list, copy or print anything under ~/edapitool" hard limit. Setting `ED_PLUGIN_DIR` to a scratch directory for every command (not just that one) closes this off unconditionally rather than relying on remembering to do it for one example. No directory listing of the real `~/edapitool/plugins` occurred at any point (verified: `ED_PLUGIN_DIR` was exported before every single `edapitool` invocation in this run).
2. **The "older shape" doc example was tested twice** (literal paste including its `//` jsonc comment, and again with that comment line removed), rather than once, because the literal paste is not valid JSON and pasting it as-is would only demonstrate a parse error rather than the shape's documented behaviour. Both results are reported above; neither is a checklist failure.
