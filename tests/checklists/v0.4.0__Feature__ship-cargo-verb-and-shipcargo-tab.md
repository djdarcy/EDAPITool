# Human Test Checklist: the `ship` verb and the ShipCargo tab

**Target version:** v0.4.0
**Ships with commit:** TBD — "Add `edapitool ship` and the generated ShipCargo tab"
**Companion automated tests:** 346 tests — `tests/test_sheets.py` (106), `tests/test_journal.py` (46), `tests/test_matcher.py` (46), `tests/test_catalog.py` (45), `tests/test_market_data.py` (32), `tests/test_service.py` (24), **`tests/test_ship.py` (20)**, **`tests/test_cli_ship.py` (13)**, `tests/test_gsheet_guard.py` (14)

## What this is

v0.4.0 adds one command, `edapitool ship`, which reads what your ship is carrying out of the game's own `Cargo.json` and can publish it as JSON, as CSV, or as a generated `ShipCargo` spreadsheet tab.

The automated tests cover the logic thoroughly, including a mutation audit. What they cannot cover is the *state of your game*: they cannot get you into an SRV, empty your hold, or catch you mid-dock while the game is rewriting the file. Nor can they tell you whether the glyph-free terminal output actually reads well, or whether the tab looks right in a browser. That is what this document is for.

One bug in this feature was found only by running it for real: the spreadsheet write passed its arguments in the wrong order and failed with `unhashable type: 'list'`. Every automated test passed, because the only test touching that path used `--dry-run`, which returns before the failing line. Section 3 exists because of it.

## Prerequisites

1. **Elite Dangerous installed**, with a journal directory. Most sections need the game to have written a `Cargo.json` at least once — it does so whenever your hold changes.
2. **Python 3.10+**, project installed with `pip install -e .`
3. **No spreadsheet is needed** for Sections 1, 2 and 4. Only Section 3 writes to one.
4. **Sections 5 needs you to change game state** (board an SRV, empty your hold). Skip it if that is inconvenient; nothing else depends on it.

**State isolation:** this command reads the journal and never writes to it. The only writes are the export files you ask for (into the current directory or `--output`) and, in Section 3, the `ShipCargo` tab. It touches no config file at all.

**Before Section 3**, note the tab it will write to. `ShipCargo` is generated wholesale — if you already have a tab by that name holding something you care about, use `--ship-tab SOMETHING_ELSE` instead.

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these five. They are the whole feature.

### HV.1 — It reads your actual hold

Validates: the extraction path end to end, against real game data.

- [ ] **Steps** (same across all shells):

  ```
  edapitool ship
  ```

- [ ] **Expected:** a timestamp, a tonnage total, a commodity count, and one line per commodity aligned in a column. The tonnage should match what the game's cargo screen shows.
- [ ] **Why this matters:** if the total disagrees with the game, every downstream number is wrong.

### HV.2 — No spreadsheet, no credentials, no login

Validates: issue #10's defect is not present here.

- [ ] **Steps** (same across all shells):

  ```
  edapitool ship --json
  ```

- [ ] **Expected:** JSON on stdout, exit code 0. **No browser window opens. No Google sign-in. No Frontier login. No error about a spreadsheet id.**
- [ ] **Why this matters:** `edapitool market --json` currently fails here demanding a sheet id (issue #10). If `ship --json` behaves the same way, the fix did not take.

### HV.3 — Commodity names come out right

Validates: symbol-first name resolution, the one trap the game sets.

- [ ] **Expected:** if you are carrying Biowaste, it reads `Biowaste` — not `biowaste`, not blank, not missing from the list.
- [ ] **Why this matters:** the game omits the display name when it equals the internal name, so a display-name-only lookup drops exactly those commodities. Biowaste is the common one.

### HV.4 — Glyph-free output renders anywhere

Validates: terminal portability.

- [ ] **Steps:** run `edapitool ship` in cmd.exe, in PowerShell, and in Windows Terminal.
- [ ] **Expected:** identical, readable output in all three. No `?` characters, no boxes, no mojibake.
- [ ] **Why this matters:** unlike the marker column, this output is plain ASCII by design. If it mangles, something introduced a non-ASCII character that should not be there.

### HV.5 — The tab write actually works (MANUAL, needs a spreadsheet)

Validates: the path that a `--dry-run`-only test could not reach.

- [ ] **Steps:**

  ```
  edapitool ship --sheet-id YOUR_SHEET_ID --export ship-tab --dry-run
  edapitool ship --sheet-id YOUR_SHEET_ID --export ship-tab
  ```

- [ ] **Expected:** the dry run lists the rows; the real run reports `tab:  ShipCargo (N commodities)`. **No `unhashable type` error.**
- [ ] **Why this matters:** this is the exact bug that shipped green. A dry run is not evidence that the real write works.

## Section 1: The generic outputs (~3 min, no spreadsheet)

### 1.1 JSON on stdout is machine-readable

- [ ] **Steps** (pick your shell):

  **cmd.exe / PowerShell / POSIX** (cross-shell, uses Python):
  ```
  edapitool ship --json | python -m json.tool
  ```

- [ ] **Expected:** parses cleanly. Top-level keys `vessel`, `is_ship`, `timestamp`, `reported_count`, `itemised_total`, `item_count`, `commodities`.
- [ ] **Check:** `itemised_total` equals the sum of the `count` values in `commodities`.

### 1.2 CSV rows are self-contained

- [ ] **Steps** (pick your shell):

  **cmd.exe**:
  ```cmd
  edapitool ship --export csv --output %TEMP%\shiptest
  type %TEMP%\shiptest\shipcargo_ship_*.csv
  ```

  **PowerShell**:
  ```powershell
  edapitool ship --export csv --output "$env:TEMP\shiptest"
  Get-Content (Get-ChildItem "$env:TEMP\shiptest\shipcargo_ship_*.csv" | Select-Object -First 1)
  ```

  **POSIX**:
  ```bash
  edapitool ship --export csv --output /tmp/shiptest
  cat /tmp/shiptest/shipcargo_ship_*.csv
  ```

- [ ] **Expected:** header `vessel,timestamp,commodity,commodity_id,symbol,count,stolen`, then one row per commodity with the vessel and timestamp repeated on every row.
- [ ] **Check:** two exports taken at different times concatenate into one file that still makes sense — that is the point of repeating the timestamp.

### 1.3 stdout JSON and file JSON agree

- [ ] **Steps** (same across all shells):

  ```
  edapitool ship --json --export json --output <a temp dir>
  ```

- [ ] **Expected:** the JSON printed to stdout is byte-identical to the JSON in the written file.
- [ ] **Why this matters:** a consumer written against one should not break when pointed at the other.

### 1.4 It works with no credentials at all

- [ ] **Steps** (pick your shell — runs with a throwaway home so no saved token or config can be found):

  **PowerShell**:
  ```powershell
  $old = $env:USERPROFILE
  $env:USERPROFILE = "$env:TEMP\edapitool-nocreds"
  New-Item -ItemType Directory -Force $env:USERPROFILE | Out-Null
  edapitool ship --json
  $env:USERPROFILE = $old
  Write-Host "restored: $env:USERPROFILE"
  ```

  **POSIX**:
  ```bash
  HOME="$(mktemp -d)" edapitool ship --json
  ```

- [ ] **Expected:** JSON, exit 0, no prompts.
- [ ] **Reset:** confirm `USERPROFILE` points back at your real profile before continuing.

## Section 2: Exit codes, for scripting (~2 min)

### 2.1 Success and failure are distinguishable

- [ ] **Steps** (pick your shell):

  **PowerShell**:
  ```powershell
  edapitool ship > $null 2>&1; Write-Host "ship            -> $LASTEXITCODE"
  edapitool ship --json > $null 2>&1; Write-Host "ship --json     -> $LASTEXITCODE"
  edapitool ship --export ship-tab > $null 2>&1; Write-Host "ship-tab, no id -> $LASTEXITCODE"
  edapitool ship --export nonsense > $null 2>&1; Write-Host "bad format      -> $LASTEXITCODE"
  ```

  **POSIX**:
  ```bash
  for a in "" "--json" "--export ship-tab" "--export nonsense"; do
    edapitool ship $a >/dev/null 2>&1; echo "  $? <- edapitool ship $a"
  done
  ```

- [ ] **Expected:** `0`, `0`, `1`, `1`.
- [ ] **Why this matters:** a script piping `--json` into `jq` must not have to parse an error message to know it failed.

### 2.2 The bad-format message names the valid ones

- [ ] **Steps:** `edapitool ship --export nonsense`
- [ ] **Expected:** names `nonsense` as unknown AND lists `csv, json, ship-tab`. A message that only says "invalid" fails this step.

## Section 3: The generated tab (MANUAL — writes to a spreadsheet) (~5 min)

> **Skip this section** if you have no spreadsheet to write to. Sections 1, 2 and 4 cover everything else.

### 3.1 Dry run first

- [ ] **Steps:** `edapitool ship --sheet-id YOUR_SHEET_ID --export ship-tab --dry-run`
- [ ] **Expected:** prints the rows it *would* write and writes nothing. Verify in the browser that no `ShipCargo` tab was created or changed.

### 3.2 The real write

- [ ] **Steps:** `edapitool ship --sheet-id YOUR_SHEET_ID --export ship-tab`
- [ ] **Expected:** `tab:  ShipCargo (N commodities)`.
- [ ] **Check in the browser** that the tab reads:

  | Row | A | B | C | D | E |
  |-----|---|---|---|---|---|
  | 1 | | Vessel | Ship | Updated (UTC) | *timestamp* |
  | 2 | | Total Tonnage | *total* | Items | *count* |
  | 3 | | Commodity | Quantity | Symbol | Stolen |
  | 4+ | | *name* | *qty* | *symbol* | 0 |

- [ ] **Check:** column A is empty on every row. This is deliberate — it is the margin, and column B is the lookup key.

### 3.3 The lookup contract holds

- [ ] **Steps:** in any scratch cell of that spreadsheet, enter:

  ```
  =IFNA(VLOOKUP("<a commodity you are carrying>", ShipCargo!$B:$C, 2, FALSE), "MISSING")
  ```

- [ ] **Expected:** the quantity you are carrying. Try it with **different capitalisation** than the tab shows — it should still match, because exact-match VLOOKUP is case-insensitive.
- [ ] **Check:** try a commodity you are NOT carrying; it should read blank, not `MISSING` and not an error.
- [ ] **Delete the scratch cell afterwards.**

### 3.4 Re-running clears what is gone

- [ ] **Steps:** note a commodity in the tab. Sell or transfer all of it in-game, open your cargo screen so the game rewrites `Cargo.json`, then re-run the export.
- [ ] **Expected:** that commodity is **absent** from the tab, not left showing its old quantity.
- [ ] **Why this matters:** the tab is rewritten wholesale precisely so a stale row cannot survive. A leftover row would feed a spreadsheet a number that looks current and is not.

### 3.5 A custom tab name is honoured

- [ ] **Steps:** `edapitool ship --sheet-id YOUR_SHEET_ID --export ship-tab --ship-tab ShipCargoTest`
- [ ] **Expected:** a tab named `ShipCargoTest` is created and written; `ShipCargo` is untouched.
- [ ] **Cleanup:** delete `ShipCargoTest` when done.

## Section 4: Refusals and error messages (~2 min)

### 4.1 No spreadsheet id, but ship-tab requested

- [ ] **Steps:** `edapitool ship --export ship-tab` (with no `--sheet-id` and none configured)
- [ ] **Expected:** the hold is still printed, *then* a clear error naming `--sheet-id`, `ED_SHEET_ID` and the config file. Exit 1.
- [ ] **Check:** the error mentions only `--export ship-tab` as the thing needing a spreadsheet — it must not suggest that `ship` in general needs one.

### 4.2 A journal directory that does not exist

- [ ] **Steps:** `edapitool ship --journal-dir /some/path/that/does/not/exist`
- [ ] **Expected:** a message naming `ED_JOURNAL_DIR` as the fix. Exit 1. No traceback.

### 4.3 A journal directory with no Cargo.json

- [ ] **Steps:** point `--journal-dir` at an empty directory containing only a `Journal.*.log` file.
- [ ] **Expected:** a message explaining that the game writes `Cargo.json` when your hold changes. Exit 1, no traceback.

## Section 5: Game-state cases (MANUAL — requires changing your game state)

> Skip if inconvenient. Nothing else depends on these, but they are the cases no fixture can build.

### 5.1 SRV cargo is refused

- [ ] **Steps:** deploy your SRV and board it, collect something so the game writes `Cargo.json` for the SRV, then run `edapitool ship`.
- [ ] **Expected:** a refusal naming the SRV, telling you to board your ship. Exit 1. It must **not** print the SRV's contents as though they were the ship's.
- [ ] **Why this matters:** both vessels write to the same file. Reporting one as the other would feed a real number about the wrong vessel into a spreadsheet.

### 5.2 An empty hold is not an error

- [ ] **Steps:** sell everything, open the cargo screen, run `edapitool ship`.
- [ ] **Expected:** reports 0 t across 0 commodities, exit 0. Not a crash, not "no data found".
- [ ] **Check:** `--export ship-tab` on an empty hold writes a tab with headers and no commodity rows — not a tab still showing the previous contents.

### 5.3 Reported total versus itemised total

- [ ] **Steps:** watch for a run where the printed note appears: *"the file reports N t total but itemises M t"*.
- [ ] **Expected:** if you never see it, that is fine — it fires only when the game's own header count disagrees with its inventory list, which may indicate a mid-write read.
- [ ] **Note it if you see it**, with the timestamp and what you were doing.

## What the automated tests DON'T cover

- **Your game's actual state.** No fixture can board an SRV, empty a hold, or catch the game mid-write. Section 5 is the only coverage of those.
- **Whether the totals match the game.** Tests compare the tool against a fixture; only you can compare it against the cargo screen.
- **What Google Sheets renders.** Tests assert the payload sent to the API, not what the browser shows.
- **Real network behaviour** — rate limits, partial failures, permission errors, a spreadsheet you lack access to.
- **Terminal rendering** across shells and codepages.
- **Whether the output is *useful*.** Tests confirm the numbers are right; only using it while trading tells you whether the shape of the command helps.

## Reporting issues found

1. Note the section and step number (e.g. "HV.5", "5.1").
2. Capture the exact command and its full output.
3. For anything spreadsheet-related, a screenshot beats a description.
4. Note your OS, shell, and — on Windows — the output of `chcp`.
5. File against issue #6, or open a new issue referencing this checklist and the v0.4.0 commit.
