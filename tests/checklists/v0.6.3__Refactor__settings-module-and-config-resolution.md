# Human Test Checklist: the settings module and config resolution

**Target version:** v0.6.3 — **pending**, the maintainer picks the bump at the release gate. If it lands differently, this file gets renamed.
**Ships with commit:** TBD (built on `5ba60b2`)
**Companion automated tests:** 543 total, up from 534 — `tests/test_daemon.py` (36), `tests/test_region_publishing.py` (24), `tests/test_destination.py` (22), `tests/test_config_regions.py` (17, up from 14), `tests/test_settings.py` (6), `tests/test_baseline_freshness.py` (6), `tests/test_capi_cooldown.py` (5)

## What this is

A structural move plus four fixes. Configuration handling — the config file and the rules for deciding where a setting comes from — was living inside the argparse module and had begun duplicating itself. It now has its own module.

Most of this is invisible if it works. That is exactly why it needs a checklist: **two of the four fixes are about data you cannot afford to lose, and a third is a behaviour that only shows up with real credentials and a real spreadsheet.** No mock proves any of them.

Run this before shipping, and re-run Section 3 after any future change to how settings are saved.

## What changed

| # | Change | Why it matters to a user |
|---|---|---|
| 1 | New `APITool/settings.py` owns the config file and the precedence resolvers | Nothing visible, unless it broke something |
| 2 | `APITool/config.py` renamed to `APITool/constants.py` | Nothing visible — but an editable install could break if the rename missed an import |
| 3 | The config file's path is built in **one** place, not four | A test could previously read your **real** config while appearing not to |
| 4 | `carrier --export google` now honours `ED_SHEET_ID` and the config file | **It previously ignored both** and demanded the flag |
| 5 | Saving the client id is now atomic | **An interrupted `auth` could previously truncate your config and take your region bindings with it** |
| 6 | First CLI-level tests of config refusals | Refusal messages are now assertable |

## Prerequisites

1. **Back up `~/.ed_capi_config.json` before doing anything.** Several steps below write to it, and since v0.6.2 it holds `construction_regions` that you typed by hand and that exist nowhere else.

   **cmd.exe**
   ```cmd
   copy "%USERPROFILE%\.ed_capi_config.json" "%TEMP%\ed_capi_config.backup.json"
   ```
   **PowerShell**
   ```powershell
   Copy-Item "$env:USERPROFILE\.ed_capi_config.json" "$env:TEMP\ed_capi_config.backup.json"
   ```
   **POSIX**
   ```bash
   cp ~/.ed_capi_config.json /tmp/ed_capi_config.backup.json
   ```

2. **An editable install** of the current working tree: `pip install -e .`
3. **Sections 1, 2 and 4 need no credentials.** Section 3 needs real Frontier credentials and a spreadsheet you own.
4. The sheet id in this repo's README is a **public template link**, not a secret. Use your own for these steps.

### Isolating the CLI from your real config

Several steps drive the CLI without touching your real settings. The config path follows `Path.home()`, which follows `USERPROFILE` on Windows and `HOME` on POSIX — so point that at a scratch directory and write a throwaway config there.

**cmd.exe**
```cmd
mkdir "%TEMP%\edscratch"
set USERPROFILE=%TEMP%\edscratch
echo {"sheet_id":"FAKE-NOT-A-REAL-SHEET"} > "%TEMP%\edscratch\.ed_capi_config.json"
```
**PowerShell**
```powershell
New-Item -ItemType Directory -Force "$env:TEMP\edscratch" | Out-Null
$env:USERPROFILE = "$env:TEMP\edscratch"
'{"sheet_id":"FAKE-NOT-A-REAL-SHEET"}' | Set-Content "$env:TEMP\edscratch\.ed_capi_config.json"
```
**POSIX**
```bash
mkdir -p /tmp/edscratch
export HOME=/tmp/edscratch
echo '{"sheet_id":"FAKE-NOT-A-REAL-SHEET"}' > /tmp/edscratch/.ed_capi_config.json
```

**Open a fresh shell when you are done**, so the override does not leak into later work.

### Reset between sections

Restore the config from the Prerequisites backup. Nothing else persists.

## High-Value Verification (~5 minutes)

### HV.1 — The rename did not break the install

Validates: change 2. A missed import is invisible until someone runs the tool on a clean machine.

- [ ] **Steps:**
  1. `pip install -e .`
  2. `python -c "from APITool import constants, settings; print('ok')"`
  3. `edapitool --version`
- [ ] **Expected:** `ok`, then a version string. No `ModuleNotFoundError` for `APITool.config`.
- [ ] **Why this matters:** the old module name is gone; anything still importing it fails at import time, which takes every command down with it.

### HV.2 — `carrier --export google` honours the config file

Validates: change 4, the one user-visible bug fix.

- [ ] **Steps:** with `sheet_id` set in `~/.ed_capi_config.json` and **no** `--sheet-id` flag, run `edapitool carrier --export google`
- [ ] **Expected:** it proceeds and exports. It must **not** print `Error: --export google needs a spreadsheet`.
- [ ] **Why this matters:** this exact command refused before this release even when a sheet id was configured, while every other verb accepted one. That divergence is the defect.

### HV.3 — Saving the client id does not eat your region bindings

Validates: change 5, the data-loss fix.

- [ ] **Steps:**
  1. Confirm `~/.ed_capi_config.json` contains a `construction_regions` list.
  2. Run `edapitool auth --client-id <your id>`.
  3. Open the config file.
- [ ] **Expected:** `client_id` is set **and** `construction_regions` is untouched, with every entry intact.
- [ ] **Why this matters:** those bindings are typed by hand and copied nowhere. A whole-file rewrite that failed partway through would take them.

### HV.4 — A bad setting still refuses the run and says where it came from

Validates: change 6, and that the move preserved the refusal semantics.

- [ ] **Steps:** using the scratch isolation above, set `"construction_regions": [{"site": "No Region Key"}]` and run `edapitool serve`
- [ ] **Expected:** exactly two lines — `Error: construction_regions[0] has no "region"` and an indented `(from <path>)` naming the config file. Exit code 1.
- [ ] **Why this matters:** a malformed entry that is skipped rather than refused is a region that quietly stops publishing with nothing said.

### HV.5 — The flag still wins outright over the file

- [ ] **Steps:** with a region in the config, run `edapitool serve --construction-region "Other (test)!A1:J40=Other Site"`
- [ ] **Expected:** the startup line names **only** the flag's region. The config region must not appear.
- [ ] **Why this matters:** merged sources mean no single place explains what will happen. This rule moved modules; confirm it survived the move.

### HV.6 — The suite is green and the config path is singular

- [ ] **Steps:** `python -m pytest -q`
- [ ] **Expected:** 543 passed.
- [ ] **Check:** `tests/test_settings.py::test_only_one_module_builds_the_config_path` passes — that is the structural guard behind change 3.

## Section 1: The move itself (~5 min, no credentials)

### 1.1 Both modules import cleanly and separately

- [ ] **Steps:** `python -c "from APITool import constants; from APITool import settings; print(constants.FLEETCARRIER_COOLDOWN, settings.CONFIG_FILE)"`
- [ ] **Expected:** `900` and the path to your config file.
- [ ] **Judgement call:** do the two names read correctly to you? `constants` = how to talk to Frontier; `settings` = what you prefer. If that split feels wrong, say so now — renaming later costs more.

### 1.2 The old module name is gone everywhere

- [ ] **Steps** (pick your shell):

  **cmd.exe**: `findstr /S /C:"from .config import" APITool\*.py`
  **PowerShell**: `Select-String -Path APITool\*.py -Pattern "from \.config import" -Recurse`
  **POSIX**: `grep -rn "from .config import" APITool/`
- [ ] **Expected:** no matches.

### 1.3 Git kept the rename as a rename

- [ ] **Steps:** `git log --follow --oneline -- APITool/constants.py | head -5`
- [ ] **Expected:** history predating the rename is visible. If it shows only one commit, the rename was recorded as delete-plus-add and the file's history is orphaned.

### 1.4 Nothing in the package imports the CLI

- [ ] **Steps:** `python -m pytest tests/test_settings.py::test_no_production_module_imports_the_cli -q`
- [ ] **Expected:** passes.
- [ ] **Why:** this property is the reason configuration went into a third module rather than the daemon importing it from `cli`. When it was violated, the daemon grew its own duplicate copy of the client-id resolver instead.

## Section 2: Sheet-id resolution, as a matrix (~10 min)

The defect fixed here was a **divergence between verbs**, so the test is a matrix rather than a single case. Use the scratch isolation for the config-file column.

For each verb below, check all three sources resolve:

| Verb | `--sheet-id` flag | `ED_SHEET_ID` | config file |
|---|---|---|---|
| `market` | [ ] | [ ] | [ ] |
| `construction --publish-to` | [ ] | [ ] | [ ] |
| `serve` | [ ] | [ ] | [ ] |
| `ship --export ship-tab` | [ ] | [ ] | [ ] |
| **`carrier --export google`** | [ ] | [ ] | [ ] |

### 2.1 Setting the environment variable

**cmd.exe**: `set ED_SHEET_ID=YOUR_SHEET_ID`
**PowerShell**: `$env:ED_SHEET_ID = "YOUR_SHEET_ID"`
**POSIX**: `export ED_SHEET_ID=YOUR_SHEET_ID`

Unset it again:

**cmd.exe**: `set ED_SHEET_ID=`
**PowerShell**: `Remove-Item Env:\ED_SHEET_ID`
**POSIX**: `unset ED_SHEET_ID`

### 2.2 Precedence within a verb

- [ ] **Steps:** set `ED_SHEET_ID` to one value and the config file to another, then pass `--sheet-id` as a third
- [ ] **Expected:** the flag wins; with no flag, the environment wins; with neither, the file is used.

### 2.3 The refusal names all three sources

- [ ] **Steps:** with no flag, no env var and no `sheet_id` in the config, run `edapitool carrier --export google`
- [ ] **Expected:** the error names the flag, the environment variable **and** the config key — not just the flag.
- [ ] **Judgement call:** does the message tell you what to do next? Before this release it named only `--sheet-id`, which was actively misleading when a config file was present.

## Section 3: The config file is written safely (~10 min) — **destructive, back up first**

### 3.1 A normal save preserves everything else

- [ ] **Steps:** with `sheet_id` and `construction_regions` both present, run `edapitool auth --client-id <id>`
- [ ] **Check:** all three keys present afterwards; the JSON still parses; region entries byte-identical.

### 3.2 A failed save leaves the original intact

Make the config read-only, then attempt a save.

**cmd.exe**
```cmd
attrib +R "%USERPROFILE%\.ed_capi_config.json"
edapitool auth --client-id TEST123
attrib -R "%USERPROFILE%\.ed_capi_config.json"
```
**PowerShell**
```powershell
Set-ItemProperty "$env:USERPROFILE\.ed_capi_config.json" -Name IsReadOnly -Value $true
edapitool auth --client-id TEST123
Set-ItemProperty "$env:USERPROFILE\.ed_capi_config.json" -Name IsReadOnly -Value $false
```
**POSIX**
```bash
chmod 444 ~/.ed_capi_config.json
edapitool auth --client-id TEST123
chmod 644 ~/.ed_capi_config.json
```

- [ ] **Expected:** a warning on stderr; the original file **completely intact and parseable**; `construction_regions` untouched.
- [ ] **Check:** no `.ed_capi_config.json.tmp` left behind in your home directory.

### 3.3 No temp file survives any failure

- [ ] **Steps** (pick your shell), after any failed save:

  **cmd.exe**: `dir "%USERPROFILE%\.ed_capi_config.json.tmp"`
  **PowerShell**: `Test-Path "$env:USERPROFILE\.ed_capi_config.json.tmp"`
  **POSIX**: `ls -la ~/.ed_capi_config.json.tmp`
- [ ] **Expected:** not found / `False`.

### 3.4 Saving when no config exists yet

- [ ] **Steps:** with the scratch isolation and **no** config file present, run `edapitool auth --client-id TEST123`
- [ ] **Expected:** the file is created containing just `client_id`. No crash about a missing file.

### 3.5 Atomicity where `os.replace` is not free — **the real-world cases**

`os.replace` is atomic within one filesystem. These are the situations where that assumption is strained, and none of them can be simulated in a test.

- [ ] **A different filesystem or a network path.** Point `USERPROFILE` (or `HOME`) at a mapped network drive or a different volume and repeat 3.1. The temp file is created beside the config, so this should still be a same-directory move — confirm it is.
- [ ] **Antivirus interference.** On Windows, real-time scanning can briefly hold a newly created file open, making the replace fail with a sharing violation. Run 3.1 a dozen times in a row and confirm none fail; if one does, the original must still be intact.
- [ ] **Case sensitivity.** On a case-insensitive filesystem confirm nothing creates a second differing-case config file.
- [ ] **Judgement call:** if a save fails for any of these reasons, is the warning intelligible to somebody who does not know what `os.replace` is?

## Section 4: Refusal messages through the real CLI (~5 min, no credentials)

Use the scratch isolation for all of these. All must exit **1** — a refusal that exits 0 is one no script will notice.

- [ ] **4.1** `construction_regions` entry with no `"region"` → names `construction_regions[0]`, then `(from <path>)`. **Exactly two lines.**
- [ ] **4.2** A valid entry first, a broken one second → names `construction_regions[1]`, **not** `[0]`.
- [ ] **4.3** `"construction_regions": [42]` → names the entry and the type it found.
- [ ] **4.4** A bare tab name with no `!range` → refused, explaining that a whole tab must be declared deliberately.
- [ ] **4.5** A bad value passed via `--construction-region` rather than the file → **exactly one line, with no trailing blank line**, and **no** `(from <path>)`, because the value did not come from the file.
- [ ] **4.6** Unreadable/corrupt config (write `not json at all` into it) → `serve` does not crash with a traceback.
- [ ] **4.7 Windows rendering:** run at least one refusal in `cmd.exe` at its default codepage. No mojibake, no `UnicodeEncodeError`.

**On 4.5 specifically:** the blank line is the regression being guarded. The code chose *which string* to print but printed unconditionally, so the flag branch emitted an empty line. Check it with a byte-accurate viewer, not by eye:

**PowerShell**: `edapitool serve --construction-region "BadValue" 2>&1 | Measure-Object -Line`
**POSIX**: `edapitool serve --construction-region "BadValue" 2>&1 | wc -l`

## The trap worth knowing before you write another test

**The config file's path is resolved once, when `settings` is imported.** Patching `Path.home()` after that point does **not** move it.

This silently broke an existing fixture during development: it patched `Path.home()` to simulate a machine that had never seen the tool, the patch stopped biting, and the test read the developer's real settings — passing or failing according to whose machine it ran on, which is the worst kind of test.

**Anyone writing a test that touches configuration must patch `settings.CONFIG_FILE` directly**, not the home directory. `tests/test_settings.py` and `tests/test_config_regions.py` both show the pattern.

## What the automated tests DON'T cover

- **`carrier --export google` resolving a real sheet id and actually exporting.** Needs Frontier credentials and a real spreadsheet. This is the fix's entire point and no mock demonstrates it.
- **A save interrupted by something real** — a full disk, a permission change mid-write, an antivirus scanner holding the temp file. Tests simulate the failure by patching `os.replace`; only a real machine produces the real failure modes.
- **`os.replace` across filesystems or onto a network path.**
- **Whether an editable install still works after the rename.** Tests import from the source tree, which would not notice a broken package definition.
- **Whether the two module names read correctly to a person.** `constants` versus `settings` is a judgement, and the cost of getting it wrong is paid later.
- **Terminal rendering** — codepage, width, wrapping.

## Known gaps, stated deliberately

- **`FreighterData` carries no timestamp (#19).** A tab written an hour ago is indistinguishable from one written a minute ago. Untouched here.
- **A binding that resolves to nothing leaves the region untouched.** This diverges from #21's criterion that it should publish an empty block — and the divergence is now **resolved and deliberate**, not open: the tool will emit `State` and `Last checked` as *data*, and the spreadsheet decides what that looks like. The tool paints nothing.
- **The 24 boolean CLI flags each support only one direction** — `--x` or `--no-x`, never both. Separate work.
- **`scripts/sync-cargo-to-sheets.py` holds a sixth copy of this resolution logic**, including a hardcoded default sheet id pointing at a **different** spreadsheet from the README's template. Untouched. Whether that script is still wanted is its own question.
