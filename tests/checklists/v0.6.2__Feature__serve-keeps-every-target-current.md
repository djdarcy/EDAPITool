# Human Test Checklist: `serve` keeps every target current

**Target version:** v0.6.2
**Ships with commit:** "Keep every target current, and say which ones those are"
**Companion automated tests:** 534 total — `tests/test_daemon.py` (36), `tests/test_region_publishing.py` (24), `tests/test_destination.py` (22), `tests/test_config_regions.py` (14), `tests/test_baseline_freshness.py` (6), `tests/test_capi_cooldown.py` (5)

## What this is

v0.6.1 taught the tool to publish a construction block into a region of a tab you already own. This release makes the background service keep that block current — along with `FreighterData`, which it had never published at all — and makes it say out loud which tabs it covers and which it does not.

The hard part is not in any of that. It is that **Frontier's fleet-carrier data lags the game**, so the refresh a cargo transfer triggers routinely reads the *old* contents. No mock can reproduce somebody else's cache, which is why Section 4 exists and why it cannot be skipped.

Run this after any change to the publish loop, the carrier publisher, or region config resolution.

## Prerequisites

1. **Elite Dangerous running**, commander logged in. Several sections need real journal events; they cannot be simulated.
2. **A fleet carrier you own**, and Frontier credentials at `~/.ed_capi_tokens.json` (run `edapitool auth` if absent). Sections 1 and 2 work without these; Sections 4 and 5 do not.
3. **A scratch tab** in your spreadsheet — duplicate a settlement tab and rename it, e.g. `Scratch (test)`. **Never point these steps at a tracker you maintain by hand.** `serve` clears a declared region on every publish.
4. The sheet id in this repo's README is a **public template link**, not a secret. Use your own spreadsheet's id for these steps.
5. **Back up your config** before Section 2, which edits it.

**Back up and restore the config** (pick your shell):

**cmd.exe**
```cmd
copy "%USERPROFILE%\.ed_capi_config.json" "%TEMP%\ed_capi_config.backup.json"
rem restore:
copy "%TEMP%\ed_capi_config.backup.json" "%USERPROFILE%\.ed_capi_config.json"
```

**PowerShell**
```powershell
Copy-Item "$env:USERPROFILE\.ed_capi_config.json" "$env:TEMP\ed_capi_config.backup.json"
# restore:
Copy-Item "$env:TEMP\ed_capi_config.backup.json" "$env:USERPROFILE\.ed_capi_config.json"
```

**POSIX**
```bash
cp ~/.ed_capi_config.json /tmp/ed_capi_config.backup.json
# restore:
cp /tmp/ed_capi_config.backup.json ~/.ed_capi_config.json
```

### Reset between sections

Stop `serve` with Ctrl+C. Restore the config from the backup above. `serve` holds no state on disk beyond the config, so a restart is a clean slate — which is itself something Section 3 checks.

## High-Value Verification (~5 minutes)

If you only have five minutes, run these six. The rest of the document is edge cases.

### HV.1 — `serve` names every target it covers

Validates: the whole of #20 — a publisher covering part of a sheet looked exactly like one covering all of it.

- [ ] **Steps:**
  1. `edapitool serve --construction-region "Scratch (test)!R1:AC60=<Your Site>" --sheet-id <ID>`
- [ ] **Expected:** a line reading `Publishing 4: market, cargo, Scratch (test)!R1:AC60, carrier`
- [ ] **Why this matters:** if the count or the names are wrong, you cannot tell from the sheet which numbers are being maintained and which are fossils.

### HV.2 — it also names what it does *not* cover

- [ ] **Steps:** run `edapitool serve --sheet-id <ID>` with **no** `--construction-region`
- [ ] **Expected:** `NOT published: any construction region -- declare one with --construction-region 'Tab!R1:AC60=Site Name'`
- [ ] **Why this matters:** the gap line is the more important half. Knowing two things are current tells you nothing about the third unless something names the third.

### HV.3 — a restart corrects the sheet immediately

- [ ] **Steps:** stop `serve`, change something in game (dock, deliver cargo), start `serve` again
- [ ] **Expected:** a `Catching up:` heading followed by one line per target, before the watch loop begins
- [ ] **Why this matters:** a restart is exactly when the sheet is most likely to be wrong, and "correct once something happens" is indistinguishable from "correct" to anyone reading it.

### HV.4 — `FreighterData` is kept current at all

- [ ] **Steps:** with `serve` running, transfer any cargo to or from your carrier
- [ ] **Expected:** within about a minute, a line `FreighterData <- <N> t on <CALLSIGN>`
- [ ] **Why this matters:** this tab was never published by the service before this release, and nothing on the tab says how old it is (#19).

### HV.5 — the carrier figure is *right*, not merely fresh

Validates: the confirmation retry, the subtlest thing in this release.

- [ ] **Steps:**
  1. Note a commodity's quantity on your carrier, in game.
  2. Transfer a large amount of it to your ship.
  3. Watch `serve` for several minutes.
  4. Compare the figure it finally writes against the carrier's inventory in game.
- [ ] **Expected:** one or more `FreighterData unchanged -- not written` lines, **then** a write carrying the corrected figure. The final figure matches the game.
- [ ] **Why this matters:** Frontier served pre-transfer contents for between 14 and 31 minutes after the journal recorded the transfer. Without the retry, that first stale read is taken as "nothing changed" and the tab keeps the wrong number.

### HV.6 — the summary counts writes, not attempts

- [ ] **Steps:** let `serve` run through several quiet polls, then Ctrl+C
- [ ] **Expected:** the `Published:` figures count only lines that actually wrote. A target that reported `unchanged -- not written` must not be counted.
- [ ] **Why this matters:** a real session reported `Agri Lrg. (ex)!R1:AC60 x19` when nineteen of those wrote nothing, which makes the summary useless as evidence of anything.

## Section 1: Declaring targets on the command line (~5 min)

### 1.1 One region

- [ ] **Steps:** `edapitool serve --construction-region "Scratch (test)!R1:AC60=<Your Site>" --sheet-id <ID>`
- [ ] **Expected:** `Publishing N: ...` includes `Scratch (test)!R1:AC60`
- [ ] **Check:** the scratch tab's R1:AC60 fills with the block after `Catching up:`

### 1.2 The flag repeats

- [ ] **Steps:** pass `--construction-region` twice, naming two different tabs or two regions of one tab
- [ ] **Expected:** both appear in the `Publishing N:` line and both publish during catch-up

### 1.3 The site may be omitted

- [ ] **Steps:** `--construction-region "Scratch (test)!R1:AC60"` with no `=Site`
- [ ] **Expected:** accepted; the block follows whichever construction site you are docked at
- [ ] **Check:** dock at a different site and confirm the block follows

### 1.4 A tab name with spaces, periods and parentheses

- [ ] **Steps:** use a tab literally named `Agri Lrg. (ex)` or similar
- [ ] **Expected:** parsed correctly — the split is on the **last** `!`, so punctuation in the name is safe
- [ ] **Judgement call:** if it fails, note the exact name; this is the class of bug that only shows up on real tab names

### 1.5 `serve --once`

- [ ] **Steps:** `edapitool serve --once --construction-region "..." --sheet-id <ID>`
- [ ] **Expected:** `Publishing 4 target(s) once.`, one line per target, then exit 0. **Every** target, not just the two generated tabs.
- [ ] **Check:** each line is a readable message. If you see anything resembling `PublishResult(wrote=True, message='...')`, that is a defect — report it.

## Section 2: Config file support (~10 min)

**Back up your config first** (see Prerequisites).

### 2.1 Objects in the config file

- [ ] **Steps:** add to `~/.ed_capi_config.json`:
  ```json
  {
    "client_id": "...",
    "sheet_id": "...",
    "construction_regions": [
      {"region": "Scratch (test)!R1:AC60", "site": "Your Site Name"}
    ]
  }
  ```
  then run `edapitool serve` with **no** flags at all
- [ ] **Expected:** the region is published, named in `Publishing N:`, with nothing typed on the command line

### 2.2 The string form also works in config

- [ ] **Steps:** replace the object with `"Scratch (test)!R1:AC60=Your Site Name"`
- [ ] **Expected:** identical behaviour. One internal shape, two spellings.

### 2.3 The flag wins outright — it does not merge

- [ ] **Steps:** with a region in config, run `serve --construction-region "Other (test)!A1:J40=Other Site"`
- [ ] **Expected:** **only** the flag's region is published. The config region must **not** appear.
- [ ] **Why:** merged sources mean no single place explains what will happen.

### 2.4 A malformed entry refuses the run and names the index

- [ ] **Steps:** set `"construction_regions": [{"site": "No Region Key"}]`
- [ ] **Expected:** the run refuses with a message naming `construction_regions[0]`, and a following line naming the config file path
- [ ] **Check:** it must **refuse**, not skip. A region silently dropped is one that quietly stops publishing with nothing said.

### 2.5 The index is the real index

- [ ] **Steps:** put a valid entry first and a malformed one second
- [ ] **Expected:** the message names `construction_regions[1]`, not `[0]`

### 2.6 Wrong type entirely

- [ ] **Steps:** `"construction_regions": [42]`
- [ ] **Expected:** refuses, naming the entry and the type it found

## Section 3: Startup catch-up (~5 min)

### 3.1 Every target publishes once at startup

- [ ] **Steps:** start `serve`, read the output above `Poll ...s, debounce ...s.`
- [ ] **Expected:** a `Catching up:` heading, then one line per target
- [ ] **Check:** this happens even when nothing has changed in game

### 3.2 A restart corrects a tab that went stale

- [ ] **Steps:**
  1. Start `serve`, let it publish, stop it.
  2. In game, deliver cargo to a construction site.
  3. Start `serve` again.
- [ ] **Expected:** catch-up writes the corrected block without waiting for a new event
- [ ] **Check:** the settlement tab's derived columns move to the new figures

### 3.3 Priming does not replay the backlog

- [ ] **Steps:** start `serve` after a long play session with many docks
- [ ] **Expected:** exactly one catch-up publish per target — **not** one per historical event
- [ ] **Check:** the catch-up block is a handful of lines, not dozens

### 3.4 A catch-up failure does not stop the run

- [ ] **Steps:** declare a region on a tab that does not exist, then start `serve`
- [ ] **Expected:** a `! <target> catch-up failed: ...` line, and `serve` continues with the other targets

## Section 4: The carrier publisher (~15 min, needs Frontier credentials)

### 4.1 It is present when credentials exist

- [ ] **Steps:** with valid credentials, start `serve`
- [ ] **Expected:** `carrier` appears in `Publishing N:`, and **no** `NOT published: FreighterData` line

### 4.2 It is absent, and says so, when they do not

- [ ] **Steps:** move `~/.ed_capi_tokens.json` aside and start `serve`

  **cmd.exe**
  ```cmd
  move "%USERPROFILE%\.ed_capi_tokens.json" "%TEMP%\tokens.aside.json"
  ```
  **PowerShell**
  ```powershell
  Move-Item "$env:USERPROFILE\.ed_capi_tokens.json" "$env:TEMP\tokens.aside.json"
  ```
  **POSIX**
  ```bash
  mv ~/.ed_capi_tokens.json /tmp/tokens.aside.json
  ```
- [ ] **Expected:** `serve` still runs, publishing the other targets, and prints `NOT published: FreighterData -- no Frontier credentials, so the carrier cannot be read. Run 'edapitool auth', or refresh it by hand with 'edapitool carrier --export google'`
- [ ] **Why this matters:** every other target reads a local file. Losing all of them because one needs a login would be the wrong trade.
- [ ] **Reset:** move the token file back.

### 4.3 It publishes last

- [ ] **Steps:** trigger several targets at once (dock at a construction site while carrying cargo)
- [ ] **Expected:** in the catch-up block and in the loop, `FreighterData` is the **last** line
- [ ] **Why:** it is the only target that leaves your machine; a slow network call must not delay three local ones.

### 4.4 A transfer triggers it

- [ ] **Steps:** with `serve` running, move cargo to or from the carrier
- [ ] **Expected:** a carrier publish attempt within roughly a minute of the transfer

### 4.5 Trading at the carrier's market triggers it too

- [ ] **Steps:** buy or sell at your carrier's own commodity market
- [ ] **Expected:** a carrier publish attempt. `MarketBuy`, `MarketSell` and `CarrierTradeOrder` are all triggers.

### 4.6 The floor holds under a burst

- [ ] **Steps:** transfer a full hold — dozens of `CargoTransfer` events in seconds
- [ ] **Expected:** **not** dozens of carrier publishes. At most one a minute.
- [ ] **Check:** count the `FreighterData` lines against the number of transfers.

### 4.7 The heartbeat fires with no events at all

- [ ] **Steps:** leave `serve` running, idle, for twenty minutes
- [ ] **Expected:** a carrier publish attempt roughly every fifteen minutes even with nothing happening
- [ ] **Why this matters:** another commander filling a buy order on your carrier changes its hold and **appears nowhere in your journal**. Event-driven alone would never notice.

### 4.8 A carrier failure does not kill the loop

- [ ] **Steps:** disconnect from the network with `serve` running, then trigger a carrier event
- [ ] **Expected:** a `! carrier publish failed: ...` line, and the loop continues publishing the local targets
- [ ] **Reset:** reconnect; the next heartbeat should succeed.

## Section 5: The confirmation retry (~20 min, the one mocks cannot reach)

This is the heart of the release. **Frontier's carrier endpoint serves a cached payload that lags the game.** Measured 2026-09-15: a transfer at 03:30:16 was still absent from Frontier's payload at 03:44:40 and had landed by 04:01:14 -- the carrier still showed 840 t of Biowaste that had already been moved into the ship, for somewhere between 14 and 31 minutes.

### 5.1 The stale read is visible

- [ ] **Steps:**
  1. Note a commodity's exact quantity on the carrier, in game.
  2. With `serve` running, transfer a large amount of it to your ship.
  3. Read every `FreighterData` line that follows.
- [ ] **Expected:** at least one `FreighterData unchanged -- not written`, because Frontier is still serving the pre-transfer figure
- [ ] **Note:** if Frontier happens to be current, you will see a write immediately. That is a valid outcome — the lag is not guaranteed, only common. Repeat the test; it is the *retry* being exercised that matters.

### 5.2 It keeps asking, once a minute

- [ ] **Steps:** after 5.1, time the gap between consecutive carrier lines
- [ ] **Expected:** roughly 60 seconds, **not** 900. Waiting a quarter of an hour to re-ask is the failure itself.

### 5.3 It stops as soon as the data changes

- [ ] **Steps:** watch until the corrected figure is written
- [ ] **Expected:** after the write, the every-minute attempts stop and the quarter-hourly heartbeat resumes
- [ ] **Check:** you are not left with a carrier call every minute forever.

### 5.4 The final figure is correct

- [ ] **Steps:** compare `FreighterData` against the carrier's inventory screen in game, commodity by commodity for at least three commodities
- [ ] **Expected:** exact match, including commodities held in more than one stack
- [ ] **Why this matters:** this is the check that would have caught the original defect. The tab said 840 t sat on the carrier while the same 840 t sat in the ship's hold.

### 5.5 It gives up eventually

- [ ] **Steps:** transfer cargo to the carrier and immediately transfer it back, so the hold ends where it started
- [ ] **Expected:** the retries stop after about thirty attempts rather than continuing indefinitely
- [ ] **Why:** a change that never lands must not leave the loop asking forever.

## What the automated tests DON'T cover

These are the reasons this document exists.

- **Frontier's cache lag.** The entire reason Section 5 exists. A mock returns what you told it to; the defect was that a *third party's* cache returned something stale, and no amount of mocking discovers that.
- **Another commander filling a buy or sell order on your carrier.** It changes the hold and appears nowhere in your journal. This is why the heartbeat exists, and it can only be observed with a second person.
- **Google Sheets quota behaviour under a real burst.** The quota is 60 writes a minute; the tests count calls against a fake worksheet, which has no quota.
- **Whether the block's row-5 alignment actually lines up on screen.** The table starts on row 5 so a commodity in the block lands beside its counterpart in a settlement tab's own column B. Only an eye can confirm that.
- **Token refresh across a multi-hour session.** Access tokens last about four hours; a test cannot wait.
- **Terminal rendering** — codepage, width, wrapping.
- **Whether the messages are actually helpful.** Every refusal in Section 2 is a judgement test: the code either refuses or it does not, and what you are assessing is whether a person reading it knows what to do next.

## Known gaps, stated deliberately

- **`FreighterData` carries no timestamp (#19).** A tab written an hour ago is indistinguishable from one written a minute ago. That is precisely how the stale carrier data in Section 5 went unnoticed until a human asked why two columns showed the same 840 t. Publishing this tab more often makes the gap matter more, not less.
- **A binding that resolves to nothing leaves the region untouched.** This diverges from #21's criterion that such a declaration "publishes an empty block and says why". It is deliberate — a name matching nothing is far more likely to be a typo in the setting than a build that vanished, and wiping a tracker over a typo is not recoverable. It is an **open decision**, not an omission.
- **The floor is not reported when it blocks a refresh.** #20 asks that a blocked refresh be reported plainly; it is currently skipped silently.
- **Targets are not selectable.** #20 asks for a way to choose which targets to publish; there is no such flag.

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command and the full `serve` output, including the `Publishing N:` line.
3. For anything in Section 5, record the **in-game** figure alongside what the tab said, and the time of each.
4. File an issue referencing this checklist and the version.
