# Human Test Checklist: a plugin's configuration is its own

**Target version:** v0.7.4
**Ships with commit:** `v0.7.4 feat(config): a plugin's configuration is its own (#27, #18)`
**Companion automated tests:** 720 passing (from 691) — `tests/test_config_regions.py` (29, retargeted from core to the plugin), `tests/test_config_surface.py` (7, new), `tests/test_plugin_loader.py` (68), `tests/test_settings.py` (12), `tests/test_supplier_registry.py` (20), the rest of the suite (584). Counts are `pytest --collect-only` figures taken after the last change, not estimates. Every new test was red-green audited; the namespace unit was mutation-swept (`tests/mutation/v0.7.4__sweep__slice-c-unit1-namespace.md`).

## What this is

`~/.ed_capi_config.json` used to be a flat file whose keys the tool parsed one by one — including one particular spreadsheet's tab names and cell ranges. This release gives it a shape: you name the places you publish to, each one says what *kind* of place it is and which plugin knows it, and each one carries a `config` block the tool hands to that plugin **without reading**. The point of this checklist is the part automation cannot vouch for: that a person's existing file keeps working untouched, that the new shape reads clearly to someone editing it by hand, and that the documentation now describes a file that actually exists.

Run it before the release ships. About fifteen minutes, or five for the High-Value section.

## Prerequisites

1. Python 3.10+, this repository installed in editable mode (`pip install -e .`), run from the repository root.
2. A journal directory to point at. Any directory works for the steps that do not need real data; a real `Saved Games\Frontier Developments\Elite Dangerous` directory is needed only where a step says so.
3. **Back up your real config file before Section 2, and restore it at the end.** There is still no environment override for its location (rough edge 3.1), so the steps that exercise the real resolution path edit the real file.

  **cmd.exe**
  ```cmd
  copy "%USERPROFILE%\.ed_capi_config.json" "%TEMP%\ed_capi_config.backup.json"
  ```
  **PowerShell**
  ```powershell
  Copy-Item "$env:USERPROFILE\.ed_capi_config.json" "$env:TEMP\ed_capi_config.backup.json"
  ```
  **POSIX**
  ```bash
  cp ~/.ed_capi_config.json /tmp/ed_capi_config.backup.json
  ```

4. **If you are an automated runner rather than a person at the keyboard:** do not read, move or modify `~/.ed_capi_config.json` or `~/.ed_capi_tokens.json` at all. Redirect the path in-process instead and leave the real files alone:

  ```python
  # any shell, as a python -c one-liner or a scratch script
  from APITool import settings
  settings.CONFIG_FILE = pathlib.Path(tmpdir) / "config.json"   # then call cli.main([...])
  ```

  Every step below that would touch the real file is marked **MANUAL** for exactly this reason.

5. **Never run `edapitool market --update-sheet` without `--dry-run`** on a workbook whose marker column holds formulas. It clears that column (#25); the guard lands in a later release. `--dry-run` is safe and is what every step here uses.

**Reset between sections:** restore your backup (step 3, reversed), or delete the throwaway file the step created.

## High-Value Verification (~5 minutes)

**If you only have five minutes**, run these six. They are the "did it ship correctly" smoke tests; each is covered in more detail below.

### HV.1 — A file written before this release still works, untouched

Validates: the deprecated `sheet_id` alias, which is what stands between an existing install and a broken one.

- [ ] **Steps** (a throwaway file, no real config touched):

  **cmd.exe**
  ```cmd
  python -c "import json,pathlib,tempfile;d=pathlib.Path(tempfile.mkdtemp());p=d/'c.json';p.write_text(json.dumps({'client_id':'x','sheet_id':'FAKE','construction_regions':[{'region':'Tab!R1:AC60','site':'Somewhere'}]}));print(p)"
  ```
  **PowerShell / POSIX**: the same one-liner; it prints the path it made.

  Then, with `<PATH>` from above:
  ```
  python -c "import pathlib,sys; from APITool import settings, loader; settings.CONFIG_FILE=pathlib.Path(r'<PATH>'); e=loader.discover().first(); print(e.name, e.target.name, e.target.kind, e.target.params, sorted(e.target.config))"
  ```
- [ ] **Expected:** `settlement default gsheet {'id': 'FAKE'} ['construction_regions']` — the old file resolves to one target named `default`, and the bindings it carried are inside that target's `config` block, not in the tool's hands.
- [ ] **Why this matters:** if this fails, every existing user's configuration stops selecting a destination the day this ships.

### HV.2 — The new shape works, and the tool reads none of the plugin's keys

Validates: the namespace itself.

- [ ] **Steps:** make a throwaway file containing:
  ```json
  {
    "targets": {
      "settlement-workbook": {
        "kind": "gsheet", "plugin": "settlement", "id": "FAKE",
        "config": {"construction_regions": [{"region": "Tab!R1:AC60", "site": "Somewhere"}]}
      }
    }
  }
  ```
  then the same `loader.discover()` one-liner as HV.1.
- [ ] **Expected:** `settlement settlement-workbook gsheet {'id': 'FAKE'} ['construction_regions']`.
- [ ] **Why this matters:** this is the shape the documentation now describes; if it does not load, the docs describe a file that does not work.

### HV.3 — `market --json` says which target a requirement came from

Validates: the `origin` prefix.

- [ ] **Steps** (needs a real spreadsheet — **MANUAL**; skip if you have none):
  ```
  edapitool market --json --journal-dir "<your journal dir>"
  ```
- [ ] **Expected:** each row under `matches` carries both `row` (unchanged from every earlier release) and `origin`, now reading `<your target name>!<tab>!<column><row>` — for example `settlement-workbook!Totals Tab!B12`. In v0.7.3 the same field read `Totals Tab!B12`; nothing was removed.
- [ ] **Why this matters:** a consumer of the JSON should be able to say which workbook a number came from, not only which tab.

### HV.4 — The configuration surface measures zero

Validates: the probe this release adds, which is the check that the namespace actually achieved something.

- [ ] **Steps** (cross-shell safe):
  ```
  python tests/one-offs/thinking/plugin-isolation/probe_no_config_knowledge.py
  ```
- [ ] **Expected:** `0 leaks   (0 parsed by core, 0 in examples)`, exit code 0, and a line listing the one block exempted as `// deprecated` — the old shape documented in `docs/configuration.md`. An exemption that is taken is always printed.
- [ ] **Why this matters:** the equivalent probe for *code* has read 0 since v0.7.0 while configuration went unmeasured; that gap is what #27 was about.

### HV.5 — `--show-formula` is byte-identical

Validates: that a release about configuration changed no output.

- [ ] **Steps.** `--show-formula` reads your configuration before it prints, and a subprocess cannot inherit an in-process redirect — so **an automated runner must point `USERPROFILE` (POSIX: `HOME`) at a scratch directory first**, or it will read the real file. A person at their own keyboard can skip the redirect; there is nothing to protect them from.

  **cmd.exe**
  ```cmd
  set PYTHONIOENCODING=utf-8
  set USERPROFILE=%TEMP%\edapitool-scratch
  edapitool market --show-formula > %TEMP%\formula-0.7.4.txt
  ```
  **PowerShell**
  ```powershell
  $env:PYTHONIOENCODING = "utf-8"
  $env:USERPROFILE = "$env:TEMP\edapitool-scratch"
  edapitool market --show-formula > $env:TEMP\formula-0.7.4.txt
  ```
  **POSIX**
  ```bash
  PYTHONIOENCODING=utf-8 HOME=/tmp/edapitool-scratch edapitool market --show-formula > /tmp/formula-0.7.4.txt
  ```
- [ ] **Expected:** identical to the same file captured from v0.7.3. On Windows a shell-redirected capture is **2013 bytes** (1960 bytes of text plus one `\r` on each of 53 lines); read in-process without newline translation it is 1960. Compare with `fc` (cmd), `Compare-Object` (PowerShell) or `diff` (POSIX) if you kept the earlier capture — the comparison is what matters, not the figure.
- [ ] **Why this matters:** the release note says nothing user-visible changed; this is the cheapest way to find out that it did.

### HV.6 — A malformed binding still refuses the run and names itself

Validates: the moved parser, and the error path a person actually meets.

- [ ] **Steps:** put `{"sheet_id": "FAKE", "construction_regions": [{"site": "No Region Key"}]}` in a throwaway file, point `settings.CONFIG_FILE` at it (HV.1's pattern) and run `edapitool serve`.
- [ ] **Expected:** exactly two lines, then exit code 1:
  ```
  Error: construction_regions[0] has no "region"
         (from <the file you pointed at>)
  ```
  No traceback, no third line, no blank line, and **no daemon starts**.
- [ ] **Why this matters:** this parser moved from the tool into the plugin in this release; the message a person sees must not have moved with it.

## Section 1: the configuration file (~5 min, no spreadsheet needed)

### 1.1 Precedence for the spreadsheet id

- [ ] **Steps:** with a throwaway file carrying **both** `"sheet_id": "BARE"` and a `gsheet` target whose `"id"` is `"FROM-TARGET"`, run:
  ```
  python -c "import pathlib; from APITool import settings; settings.CONFIG_FILE=pathlib.Path(r'<PATH>'); print(settings.get_sheet_id())"
  ```
  Then repeat with `ED_SHEET_ID` set, and again passing `--sheet-id` to a real command.
- [ ] **Expected:** `FROM-TARGET` from the file; `ED_SHEET_ID` beats it; `--sheet-id` beats both. The bare `sheet_id` is last, which is what makes it an alias rather than a competitor.
- [ ] **Check:** a `jsonl`-kind target listed *before* the sheet target does not win — only a `gsheet` target carries a spreadsheet id.

### 1.2 A malformed entry is refused by name

- [ ] **Steps:** try each of these in a throwaway file and run any command that needs a destination (`edapitool market --no-sheet --journal-dir <dir>`):
  1. `{"targets": {"mine": {"kind": "gsheet"}}}` — no plugin
  2. `{"targets": {"mine": {"plugin": "settlement"}}}` — no kind
  3. `{"targets": {"mine": {"kind": "gsheet", "plugin": "settlement", "config": "nope"}}}` — config is not an object
  4. `{"targets": []}` — targets is not an object
- [ ] **Expected:** one `Error:` line each, naming the offending entry — `targets['mine'] has no "plugin"`, `targets['mine'].config must be an object, got str`, and so on. Never a traceback, never a silently skipped target.
- [ ] **Check:** the message names the entry by the key *you* chose, so you can find it in your own file.

### 1.3 Core reads no key of a plugin's

- [ ] **Steps** (cross-shell safe):
  ```
  python -m pytest tests/test_config_surface.py -q
  python -m pytest tests/test_config_regions.py -q
  ```
- [ ] **Expected:** 7 and 31 passing. The first file asserts the probe reads zero *and* that it can still see a planted leak; the second drives the moved parser and the CLI through both config shapes.

### 1.4 A plugin with no bindings publishes no regions

- [ ] **Steps:** configure a target naming a plugin that has no `construction_regions` function (any user plugin, or the planted one the suite uses), with a `construction_regions` list in its `config` block anyway. Run `edapitool serve` against it.
- [ ] **Expected:** it starts (or fails on the spreadsheet, if the id is fake) **without** publishing any region, and without an error about the list. The question is the plugin's to answer; a plugin that does not answer it has no regions.

## Section 2: the real file and the real sheet (~5 min, MANUAL)

Every step here is **MANUAL** — it needs your own configuration or your own spreadsheet. Back up your config first (Prerequisites, step 3).

### 2.1 Your existing file, unchanged — MANUAL

- [ ] **Steps:** with your real config exactly as it was before this release, run:
  ```
  edapitool market --dry-run --journal-dir "<your journal dir>"
  ```
- [ ] **Expected:** the same comparison you got from v0.7.3. Nothing asks you to change the file; nothing warns about a missing `targets`.
- [ ] **Check:** `edapitool market --json` shows `origin` prefixed with `default!` — the name the alias gives your file's implicit target. If you would rather it said something meaningful, that is the cue to migrate (2.2).

### 2.2 Migrating by hand, following only the documentation — MANUAL

- [ ] **Steps:** open `docs/configuration.md` and follow its "The older shape still works" table to rewrite your own file into the `targets` shape. Do not read the source. Then re-run 2.1.
- [ ] **Expected:** the same output as before the migration, with `origin` now carrying the target name you chose.
- [ ] **Why this matters:** the table is the only migration instruction a user will ever get. If you cannot follow it without reading the code, it is wrong.

### 2.3 The dry-run plan is unchanged — MANUAL

- [ ] **Steps:**
  ```
  edapitool market --update-sheet --dry-run --journal-dir "<your journal dir>"
  ```
- [ ] **Expected:** the same three ranges, in the same order, as v0.7.3 produced. **Do not run this without `--dry-run`** — the real write clears the marker column (#25) and its guard is not in this release.

### 2.4 `serve` starts and polls — MANUAL

- [ ] **First: check whether a daemon is already running.** If one is, leave it alone and skip this step.
- [ ] **Steps:** `edapitool serve` with your migrated config, for one cycle, then Ctrl+C.
- [ ] **Expected:** the same startup banner as v0.7.3, the same target list, and your construction regions still listed — now read from the target's `config` block rather than the top level. Ctrl+C still reports what it actually wrote.

## Section 3: known rough edges

These are known and deliberate. Note them if they bite; they are not new failures.

### 3.1 Still no environment override for the config file's location

Unchanged from v0.7.2, and more visible now that configuration carries more: there is no `ED_CONFIG_FILE`, so exercising the real resolution path means editing the real file. This checklist works around it by redirecting `settings.CONFIG_FILE` in-process. Worth adding before configuration grows again.

### 3.2 A whitespace-only `site` survives in a `config` block

`{"site": ""}` becomes "whichever site I am docked at"; `{"site": "   "}` stays three spaces. The command-line spelling strips before testing, the block's does not. Pre-existing, carried unchanged by this release's verbatim move, and pinned as it is by `test_an_empty_site_means_the_same_as_an_absent_one` rather than quietly changed inside a move.

### 3.3 `kind` selects the enforcer, not yet the adapter

`kind` is documented as selecting both how the tool talks to a target and what bounds its writes. The enforcer half is real (a `gsheet` target's write guard comes from its declaration). The adapter half is not yet exercised, because `gsheet` is the only kind that exists — a second kind arrives in the next release, and #27's third criterion stays partial until it does.

### 3.4 An empty `targets` map means the same as no map at all

`{"targets": {}}` falls back to enabling the shipped plugins, exactly as a file with no `targets` key does — so there is no way to say "load nothing" by emptying the map. Found by the first run of this checklist; documented in `docs/configuration.md` as of this release, and it is one of the cases the "ships no destination" ruling will settle.

### 3.5 `ED_SHEET_ID` alone synthesises a target

If the environment names a sheet and the file names neither `sheet_id` nor `targets`, a `default` target is synthesised from the environment variable. That is consistent — the variable has always been a way to name a sheet without editing the file — but it means an environment variable can bring a destination into being, which the documentation now says out loud. Found by the first run of this checklist.

### 3.6 Two targets naming one plugin: the first wins, silently

You may point two targets at the same plugin. The first one listed is the one that plugin is handed — the same precedence the loader uses everywhere — and nothing tells you the second was not used. Pinned by `test_the_first_target_naming_a_plugin_is_the_one_it_is_handed`; a `plugins` verb that would show it is the next release's.

## What the automated tests DON'T cover

- **A real spreadsheet**: every reader and writer test uses a fake worksheet. HV.3, 2.1–2.4 are the only real reads.
- **Editing the file by hand**: whether the new shape is *pleasant* to type, whether a trailing comma or a tab-indented block trips you up, whether the error message points at the right place in a file you wrote yourself.
- **The migration instruction**: 2.2 is the only test of whether `docs/configuration.md` can actually be followed.
- **`serve` over time**: the suite stubs the daemon builder by construction (a test asserting a refusal must not be able to start a real publish loop).
- **Windows console rendering** of `--show-formula` without `PYTHONIOENCODING=utf-8`.
- **Concurrency**: two processes writing the config file at once.
