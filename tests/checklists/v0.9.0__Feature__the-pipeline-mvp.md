# Human Test Checklist: the pipeline -- an ordered step list, and serve runs it

**Target version:** 0.9.0
**Ships with commit:** TBD, over `8dc8703` (units 1-3: `86d4e3c`, `c127391`, `8dc8703`)
**Companion automated tests:** 5 in `tests/test_pipeline.py` (the runner and the bound view), 3 in `tests/test_pipeline_steps.py` (two targets end to end against fakes), 7 in `tests/test_pipeline_config.py` (the key's shape, the derived order, six refusals by wording, two command paths with the daemon builder patched to raise), 8 in `tests/test_plugin_docs.py` (the page's worked examples load through the real loader). Suite: 1,093.

## What this is

Until 0.9.0, `market` and `serve` ran exactly one plugin -- the first enabled target whose plugin had a place of its own -- and a second target that also wanted to run was left out without a word. Now the tool reads the market and hands the result to each enabled plugin's step in turn, in an order you can set with a `pipelines` key or leave derived from your targets. The automated tests prove this against an in-memory sheet and a file under a temp directory. This checklist covers the real spreadsheet, the real file, a real `serve`, the config the tool writes on a first run, and the two pages that document it. About 20 minutes; the sections are independent once the prerequisites hold.

## Prerequisites

1. EDAPITool installed from this tree as an editable package, and Google Sheets access that already works. After the 0.9.0 commit, `edapitool --version` reports a version beginning `0.9.0`. If it reports `0.8.4`, the installed tree is behind: reinstall or check out the commit.
2. **A `serve` from an older tree must not be running.** Stop it before starting; restart it at the end (Cleanup).
3. **Back up your config before anything writes.** Every write step below is run as a dry run first. The spreadsheet is your own; nothing here touches the template workbook.

   **cmd.exe**:
   ```cmd
   copy "%USERPROFILE%\edapitool\config.json" "%USERPROFILE%\edapitool\config.json.pre-0.9.0"
   ```

   **PowerShell**:
   ```powershell
   Copy-Item "$env:USERPROFILE\edapitool\config.json" "$env:USERPROFILE\edapitool\config.json.pre-0.9.0"
   ```

   **POSIX**:
   ```bash
   cp ~/edapitool/config.json ~/edapitool/config.json.pre-0.9.0
   ```

4. A docked station with a commodity market, for the live steps in Sections 2, 3 and 6. The game need not be running for Sections 1, 4, 5, 7 and 8.
5. **Reset between sections:** restore `config.json` from the backup, delete the test file (Cleanup names it), and run `edapitool plugins` to confirm the pipeline reads `1. totals-workbook   totals` again.

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these five. They are the "did the work actually ship" checks; every one is covered in more detail below.

### HV.1 -- The tool says what it will run

Validates: the pipeline is derived from the enabled targets and shown in one place.

- [ ] **Steps** (same across all shells):
  ```
  edapitool plugins
  ```
- [ ] **Expected:** a section `Pipeline market (derived from the enabled targets):` listing `1. totals-workbook   totals` (your target's name may differ). The `regions` target, if you have one, is **not** in the pipeline: it offers no step. No `REFUSED` line.
- [ ] **Why this matters:** this section is the whole point of the slice -- one place that says "this runs, then this". If it is missing or lists the wrong targets, nothing below is trustworthy.

### HV.2 -- A dry run of the roll-up tab is byte-for-byte what 0.8.4 produced

Validates: one target behaves exactly as before.

- [ ] **Steps:** at a docked station, `edapitool market --update-sheet --dry-run`. If you kept a 0.8.4 run's output, compare; otherwise read the plan for the ranges and values you expect.
- [ ] **Expected:** the same plan: the same marker range, the same glyphs, the location cells only if you passed `--write-location`. No new lines about pipelines (that line is `serve`'s), no error.
- [ ] **Why this matters:** the automated goldens prove this for a fixture; this proves it for your workbook.

### HV.3 -- Two targets, both run, and the file carries the comparison

Validates: the configuration the stock config has recommended since 0.7.8 now does what it says.

- [ ] **Steps:** Section 3, steps 3.1 to 3.3.
- [ ] **Expected:** `plugins` lists two steps; the dry run says `would append 1 record`; the real run writes the sheet as before and one JSON line whose `requirements` list names the same rows the marker plan marked.
- [ ] **Why this matters:** this is the defect the slice fixes. Before 0.9.0 this configuration wrote nothing to the file and said nothing.

### HV.4 -- A pipeline that cannot run is refused by name, and `serve` stops

Validates: nothing is silently dropped.

- [ ] **Steps:** Section 5, steps 5.1 to 5.3.
- [ ] **Expected:** `plugins` prints a `REFUSED` line naming `nothere`; `market --no-sheet --json` prints the error and still prints the market; `serve --once` exits 1 without touching the sheet.
- [ ] **Why this matters:** a refusal that did not stop `serve` would be the old failure in a new costume.

### HV.5 -- `serve` prints its pipeline and every step writes

Validates: the daemon runs the same list as `market`.

- [ ] **Steps:** Section 6, step 6.1.
- [ ] **Expected:** the first lines of `serve --once --write-location` include `Pipeline market: totals-workbook -> market-log (derived from the enabled targets)`; the generated tabs, the location cells and one file record are all written.
- [ ] **Why this matters:** `serve` had its own hand-written list before; now it has none.

## Section 1: what the tool says (no game, no writes)

### 1.1 The pipeline section

- [ ] **Steps** (same across all shells):
  ```
  edapitool plugins
  ```
- [ ] **Expected:** between the `Loaded` section and `Available but not loaded`, a `Pipeline market (derived from the enabled targets):` section with one numbered line per step: position, target name, plugin name. A `regions` target is not listed. `jsonl` appears under `Available but not loaded` if you have not configured it.
- [ ] **Check:** the column alignment reads cleanly in your terminal (the target name is padded to 17 characters).

### 1.2 What a plugin's step needs

- [ ] **Steps:**
  ```
  edapitool plugins describe totals
  edapitool plugins describe jsonl
  ```
- [ ] **Expected:** `totals` shows `supplies   requirements` and `process    needs: requirements`. `jsonl` shows `supplies   previous` and `process    needs: (nothing)`. No line says `subscribes`.
- [ ] **Check:** `edapitool plugins help` describes `describe` as showing "its step's needs".

## Section 2: the single target, live (dry run only)

### 2.1 The roll-up plan is unchanged

- [ ] **Steps:** at a docked station:
  ```
  edapitool market --update-sheet --dry-run
  ```
- [ ] **Expected:** the plan you are used to. The command prints no pipeline line and no refusal. Exit 0.
- [ ] **Check:** `--write-location` still adds the two location cells to the plan and nothing else changes.

## Section 3: two targets (the fix)

### 3.1 Add a file target

- [ ] **Steps:** edit `config.json` and add, inside `"targets"`, after your totals target:
  ```json
  "market-log": {
    "kind": "jsonl",
    "plugin": "jsonl",
    "path": "~/edapitool/pipeline-test.jsonl",
    "config": {}
  }
  ```
  Then:
  ```
  edapitool plugins
  ```
- [ ] **Expected:** the pipeline section now lists two steps, your totals target first and `market-log` second (the order they appear in `targets`). `jsonl` moves from `Available` to `Loaded`.

### 3.2 A dry run writes nothing, and says so for both

- [ ] **Steps:** at a docked station:
  ```
  edapitool market --update-sheet --dry-run
  ```
- [ ] **Expected:** the marker plan as in 2.1. Exit 0.
- [ ] **Check:** the file does not exist yet.

  **cmd.exe**: `if exist "%USERPROFILE%\edapitool\pipeline-test.jsonl" echo EXISTS`
  **PowerShell**: `Test-Path "$env:USERPROFILE\edapitool\pipeline-test.jsonl"` prints `False`
  **POSIX**: `ls ~/edapitool/pipeline-test.jsonl` says no such file

### 3.3 A real run writes both

- [ ] **Steps:** at the same station:
  ```
  edapitool market --update-sheet
  ```
- [ ] **Expected:** the sheet is written as it was in 0.8.4 (open it and look at the marker column). The command's status reports the ranges written.
- [ ] **Check:** the file holds exactly one line, and it is JSON with `checked_at`, `system`, `station`, `market_id` and a `requirements` list whose `name` values are the commodities the marker plan marked.

  **cmd.exe**: `type "%USERPROFILE%\edapitool\pipeline-test.jsonl"`
  **PowerShell**: `Get-Content "$env:USERPROFILE\edapitool\pipeline-test.jsonl"`
  **POSIX**: `cat ~/edapitool/pipeline-test.jsonl`

  Cross-shell: `python -c "import json,pathlib;[print(json.loads(l)['station'], len(json.loads(l)['requirements'])) for l in pathlib.Path.home().joinpath('edapitool','pipeline-test.jsonl').read_text().splitlines()]"`

### 3.4 A second run appends, not overwrites

- [ ] **Steps:** run 3.3's command again.
- [ ] **Expected:** two lines in the file. The sheet shows no change (the marker column already held these values; the writes ledger leaves them).

## Section 4: choosing the order

### 4.1 The `pipelines` key reverses the order

- [ ] **Steps:** add at the top level of `config.json` (beside `"targets"`, not inside it), using your totals target's real name:
  ```json
  "pipelines": {
    "market": {"reads": "market", "steps": ["market-log", "totals-workbook"]}
  }
  ```
  Then `edapitool plugins`.
- [ ] **Expected:** `Pipeline market (from "pipelines"):` with `market-log` first and the totals target second.

### 4.2 Order does not change what the roll-up step reads

- [ ] **Steps:** at a docked station, `edapitool market --update-sheet --dry-run`.
- [ ] **Expected:** the same plan as 2.1. The totals step reads its own tab wherever it sits in the list.

## Section 5: refusals

### 5.1 A target that does not exist

- [ ] **Steps:** change the `steps` list to `["nothere", "totals-workbook"]`, then:
  ```
  edapitool plugins
  ```
- [ ] **Expected:** the pipeline section lists no steps and one line: `REFUSED   pipeline 'market' names target 'nothere', which is not configured`.

### 5.2 `market` says so and still answers

- [ ] **Steps:**
  ```
  edapitool market --no-sheet --json
  ```
- [ ] **Expected:** the first lines are `Error: the market pipeline cannot run:`, the refusal, and a line pointing at `edapitool plugins` and the config file; then the JSON market report. Exit 0.
- [ ] **Check:** `edapitool market --update-sheet --dry-run` prints the same error and exits 1 -- a write was asked for and the pipeline cannot run.

### 5.3 `serve` refuses before touching anything

- [ ] **Steps:**
  ```
  edapitool serve --once
  ```
- [ ] **Expected:** the error and the refusal, exit 1, and no `Pipeline market:` line -- the daemon was never built. The sheet is untouched.

### 5.4 A kind this release does not run

- [ ] **Steps:** change `"reads": "market"` to `"reads": "cargo"` (and restore the steps list to the two real targets), then `edapitool plugins`.
- [ ] **Expected:** one `REFUSED` line containing `this release runs only the 'market' pipeline reading 'market'`.
- [ ] **Check:** remove the whole `"pipelines"` key when done; `plugins` returns to `(derived from the enabled targets)`.

## Section 6: `serve`

### 6.1 Every step writes

- [ ] **Steps:** with both targets and no `pipelines` key, at a docked station:
  ```
  edapitool serve --once --write-location
  ```
- [ ] **Expected:** among the first lines, `Pipeline market: totals-workbook -> market-log (derived from the enabled targets)` (your target's name). MarketData and ShipCargo are written as before; the location cells are written; one more line lands in the file.

### 6.2 Without the flag, the roll-up tab is left alone

- [ ] **Steps:** `edapitool serve --once`
- [ ] **Expected:** the location cells are not written (open the tab and check), and one more line still lands in the file -- the file step writes on every publish, as the CHANGELOG says.

## Section 7: the config the tool writes

### 7.1 The stock header shows the pipeline

- [ ] **Steps** (pick your shell; the directory must be empty and must not be your real one):

  **cmd.exe**:
  ```cmd
  mkdir %TEMP%\edstock
  set ED_CONFIG_DIR=%TEMP%\edstock
  edapitool plugins
  type %TEMP%\edstock\config.json
  set ED_CONFIG_DIR=
  ```

  **PowerShell**:
  ```powershell
  New-Item -ItemType Directory -Force "$env:TEMP\edstock" | Out-Null
  $env:ED_CONFIG_DIR = "$env:TEMP\edstock"
  edapitool plugins
  Get-Content "$env:TEMP\edstock\config.json"
  Remove-Item Env:\ED_CONFIG_DIR
  ```

  **POSIX**:
  ```bash
  mkdir -p /tmp/edstock
  ED_CONFIG_DIR=/tmp/edstock edapitool plugins
  cat /tmp/edstock/config.json
  ```
- [ ] **Expected:** the header's comments include the `nightly-dump` jsonl example, a sentence that both targets then run in order, and a commented `"pipelines"` block naming `totals-workbook` and `nightly-dump`. The JSON below the header parses: `python -m json.tool` on the part after the last `#` line succeeds (or `edapitool plugins` loaded it, which is the same proof).

## What the automated tests DON'T cover

- A real Google Sheet: that the marker column, the location cells and the generated tabs land where they did in 0.8.4, with two steps in the list.
- A real file under your home directory: that `~` expands, that the directory is created, that records append across runs.
- A real `serve`: the startup line, the publish cadence with two steps, and the file growing one line per publish.
- The config the tool writes on a first run, as a person reads it: whether the header's commented `pipelines` block is clear enough to copy.
- The refusal messages as a person meets them: whether they say enough to fix the config without reading the docs.
- The two docs pages rendered, with their links resolving.
- Windows terminal rendering of the `plugins` listing's columns.

## Known limits, by design

- Only the `market` pipeline runs in 0.9.0. Naming another pipeline, or another data kind, is refused rather than ignored; chaining named pipelines from the command line is a later release.
- One target per plugin. Two targets naming the same plugin cannot both be steps; the second is refused by name.
- A `serve` with a loaded plugin that offers no step and no bindings still runs, keeping the generated tabs current; it is not an error.

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command and its output, and the `edapitool plugins` listing at the time.
3. Keep the `config.json` that produced it (with the sheet id removed).
4. File an issue referencing this checklist and #35.

## Cleanup

1. Decide whether to keep the `market-log` target. If not, remove it from `config.json`; if you kept a `pipelines` key for testing, remove it too.
2. Delete the test file:

   **cmd.exe**: `del "%USERPROFILE%\edapitool\pipeline-test.jsonl"`
   **PowerShell**: `Remove-Item "$env:USERPROFILE\edapitool\pipeline-test.jsonl"`
   **POSIX**: `rm -f ~/edapitool/pipeline-test.jsonl`

3. If anything looks wrong, restore `config.json` from `config.json.pre-0.9.0`.
4. Remove the scratch stock-config directory from Section 7 (`%TEMP%\edstock`, `$env:TEMP\edstock`, `/tmp/edstock`).
5. Restart your real `serve`.
