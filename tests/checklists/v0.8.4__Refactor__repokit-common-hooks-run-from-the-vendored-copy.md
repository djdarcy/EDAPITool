# Human Test Checklist: repokit-common vendored, versioning and hooks

**Target version:** 0.8.4 (with 0.8.3, which vendored repokit-common v0.2.12; 0.8.4 pulls v0.3.1)
**Ships with commit:** TBD (v0.8.4 build(repokit): ...)
**Companion automated tests:** none added in EDAPITool. The suite (1074 tests) is unchanged and must stay green. The vendored repokit-common v0.3.1 carries its own 145 tests (not collected here), including `test_install_hooks.py`, which drives a consumer through the stubs.

## What this is

EDAPITool carries the shared git-repokit-common scripts as a git subtree at `scripts/repokit-common/` (v0.3.1). It configures them under `[tool.repokit-common]` in `pyproject.toml` and uses repokit-common's git hooks in place of the ones the RepoKit generator installed in January. Nothing in the installed package changes. What changes is what happens when a developer commits and pushes, which no unit test here exercises. A maintainer runs this checklist in a real clone. About 10 minutes.

**Hooks are installed once per clone** with `bash scripts/repokit-common/install-hooks.sh`. The installer writes small **stubs** into `.git/hooks` that run the hooks from the vendored copy, so a later `git subtree pull` updates the hooks with no reinstall. The flip side: **the next commit after a pull runs whatever was pulled.**

## Prerequisites

1. A clone of EDAPITool at this version, with Python 3.11+ (or `tomli`), and the package installed editable (`pip install -e .`). The pre-push runs `python -P -m pytest`, which does not put the checkout on the import path.
2. Hooks installed: `bash scripts/repokit-common/install-hooks.sh`. The first time over non-stub hooks, it asks `y/n`; answer `y`. Git for Windows ships `bash`, so the command is the same in every shell.
3. For the commit and push steps, use a **throwaway clone** so nothing real is committed or pushed. Make it with `git clone <your clone path> <scratch>`, then run `bash scripts/repokit-common/install-hooks.sh` from inside it. Run every git command with `-C <scratch>`, and give every commit `-c user.email=t@example.com -c user.name=tester -c commit.gpgsign=false`. Never change global git config.

## High-Value Verification (~5 minutes)

### HV.1 -- The hooks are stubs that point at the vendored copy

- [ ] **Steps:** view `.git/hooks/pre-commit` (cmd.exe `type .git\hooks\pre-commit`, PowerShell `Get-Content .git\hooks\pre-commit`, POSIX `cat .git/hooks/pre-commit`). Repeat for `post-commit` and `pre-push`. Also run `git config core.hooksPath`.
- [ ] **Expected:** each starts with `# repokit-common hook stub` and names `REPOKIT_INSTALLED_DIR='scripts/repokit-common'`; about 33 lines each. `core.hooksPath` prints nothing.
- [ ] **Why this matters:** a full copy of a hook goes stale on the next pull; a stub cannot.

### HV.2 -- The settings are found and read

- [ ] **Steps (same in every shell):**
  ```
  python scripts/repokit-common/repokit_config.py --where
  python scripts/repokit-common/repokit_config.py --get print-warning
  python scripts/repokit-common/sync-versions.py --check
  ```
- [ ] **Expected:** the repo root's `pyproject.toml`; `false`; `Version: 0.8.4 ...` with no `$PACKAGE_NAME` and no parser warning.
- [ ] **Why this matters:** without the table, the version tool falls back to placeholder paths and stamps nothing.

### HV.3 -- A commit stamps the version

- [ ] **Steps:** in the throwaway clone, edit a comment in any tracked `.py` file, then run `git -C <scratch> -c user.email=t@example.com -c user.name=tester -c commit.gpgsign=false commit -am probe` and then `git -C <scratch> show HEAD:APITool/version.py`, filtered for `__version__` (cmd.exe `| findstr __version__`, PowerShell `| Select-String __version__`, POSIX `| grep __version__`).
- [ ] **Expected:** `__version__ = "0.8.4_main_<count>-<YYYYMMDD>-<parent hash>"`. Afterwards `APITool/version.py` shows as modified in the working tree; that is the known one-commit lag.
- [ ] **Why this matters:** the stamp is the one thing the old hooks did that must not regress.

### HV.4 -- A push runs the suite, and the print warning stays quiet

- [ ] **Steps:** in the throwaway clone, `git -C <scratch> push --dry-run origin HEAD:refs/heads/probe`. A dry run still runs the pre-push hook, and pushing to a new branch name avoids touching `main`.
- [ ] **Expected:** the syntax check passes, then the tests run and `1074 passed` is reported, and there is **no** warning about `print()` calls. A console shows `✓`/`⚠`; an IDE git panel shows `[OK]`/`[!]`.
- [ ] **Why this matters:** this gate is what stops a broken `main` from reaching GitHub.

### HV.5 -- `gh_issue_full.py` works from the vendored path

- [ ] **Steps:** `python scripts/repokit-common/gh_issue_full.py 9`
- [ ] **Expected:** issue #9 of this repo, printed in full with no truncation tip; `--no-full` truncates.

## Section 1: The stubs across branches

### 1.1 A branch with no vendored copy warns, and does not block

- [ ] **Steps:** in the throwaway clone, `git -C <scratch> switch dev`, make a trivial commit with the scratch identity options, then `git -C <scratch> switch main`.
- [ ] **Expected:** `repokit-common: warning -- pre-commit checks skipped: this checkout has no repokit-common copy (branch 'dev').` The commit goes through.

### 1.2 A pull updates the hooks without a reinstall

- [ ] **Steps:** in the throwaway clone, change one `echo` line in `scripts/repokit-common/hooks/pre-commit` (a stand-in for a pull), then commit.
- [ ] **Expected:** the changed line shows in the commit output. No installer was run. Restore with `git -C <scratch> checkout -- scripts/repokit-common/hooks/pre-commit`.

## Section 2: What the first hooked commits change

### 2.1 The CHANGELOG's [Unreleased] link

- [ ] **Steps:** look at the bottom of `CHANGELOG.md`.
- [ ] **Expected:** `[Unreleased]: https://github.com/djdarcy/EDAPITool/compare/v0.8.4...HEAD`, kept current by the pre-commit hook. It resolves only once `v0.8.4` is tagged.

### 2.2 Private content is still blocked on main

- [ ] **Steps:** in the throwaway clone, create `debug.log`, run `git -C <scratch> add -f debug.log`, and attempt a commit.
- [ ] **Expected:** "COMMIT BLOCKED" naming `debug.log`. A file named `catalog.py` must **not** be blocked.

## What the automated tests DON'T cover

- Real hooks on this repository's own commits and pushes, in Git for Windows' `sh`.
- The installer's interactive `y/n` prompt.
- How `✓`/`⚠` versus `[OK]`/`[!]` render in the maintainer's terminal and IDE.
- The stamped version string after a real commit, and the post-commit lag.

## Reporting issues found

Note the section and step, the exact command and output, and the shell. Save `git -C <scratch> log -1 --stat` and the hook's output.

## Cleanup

Delete the throwaway clone: cmd.exe `rmdir /s /q <scratch>`; PowerShell `Remove-Item -Recurse -Force <scratch>`; POSIX `rm -rf <scratch>`.

To return a real clone to the previous hooks, copy a `.git/hooks/<hook>.backup-<timestamp>` file over `.git/hooks/<hook>`.
