## What the sweep found that the tests did not

**Re-triaging the ledger caught a real defect.** `equivalents.md` carried an entry for `writer.py` under the hash `c8cb5c536277`, which this change invalidated. Its argument — *"the updates list always carries `marker_range(last_data_row)` spanning exactly those cells"* — was no longer true, because the plan now carries free runs rather than one wide range.

Following that argument out led to something the tests had missed entirely: **formats were still being emitted for skipped rows.** The plan would report "left alone: L5" and then paint L5's background anyway. Colour is a write, and the project had already ruled on exactly this for `--no-markers` (*"painting a formula cell green would not destroy the formula, but it would be an unasked-for edit to a column the tool no longer owns"*). Fixed by filtering `plan.formats` against `plan.skipped`, covered by `test_a_skipped_cell_is_not_coloured_either`, and anchored as revert E12 in the red-green driver.

M20 was then added by hand to check the new filter, and it is killed.

## Anomalies

**Round 1 raised two; both were resolved before the verdicts above were trusted.**

1. **M15 apply-failed** — *"expected exactly 1 occurrence of the original text in APITool/cli.py, found 0"*. The generator had inferred an indentation for the `if head == tail` line that the file does not have; it sits at the end of the preceding line. Anchor corrected, mutant then applied and eventually killed.

2. **A `UnicodeDecodeError` in the harness's subprocess reader thread**, verbatim:

   ```
   UnicodeDecodeError: 'charmap' codec can't decode byte 0x8f in position 4517:
   character maps to <undefined>
   ```

   Cause: the harness runs the child with `subprocess.run(..., text=True)` and no explicit `encoding`, so the parent decodes using the Windows locale (cp1252). The suite prints the glyph markers (`● ◕ ◑ ◔ ○`), which cp1252 cannot decode. **Verdicts were not corrupted** — the harness derives them from the child's return code, and the `(proc.stdout or "")` fallback degrades to an empty capture rather than a wrong answer — but one run's captured output was lost.

   Worked around by running the harness under `python -X utf8`, which makes the parent's preferred encoding UTF-8. The durable fix belongs in the harness (`encoding="utf-8", errors="replace"` on that `subprocess.run`) and is not made here, because this repository does not own that file.
